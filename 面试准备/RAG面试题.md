# RAG 面试题

## 1. 什么是 RAG？请介绍 RAG 系统的工作流程。

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将**外部知识检索**与 **LLM 生成**结合起来的技术。它在回答问题前，先从知识库中查找相关资料，再将资料和用户问题一起交给 LLM，从而提升答案的准确性、时效性和可追溯性，并减少幻觉。

RAG 系统通常分为两个阶段：

### 一、离线知识库构建

1. **数据采集**：获取文档、网页、数据库、PDF 等原始数据。
2. **解析与清洗**：提取正文，去除乱码、重复内容和无关信息。
3. **文本切分（Chunking）**：将长文档切成适合检索的小块，并保留标题、来源等元数据。
4. **向量化（Embedding）**：使用 Embedding 模型将文本块转换为向量。
5. **建立索引**：将文本、向量和元数据写入向量数据库或搜索引擎。

### 二、在线检索与生成

1. **处理用户问题**：对问题进行理解、改写或拆分，得到更适合检索的 Query。
2. **召回（Retrieval）**：通过向量检索、关键词检索或混合检索找出相关文本块。
3. **过滤与重排（Rerank）**：过滤无关内容，并将相关性更高的结果排在前面。
4. **构造上下文**：将选出的资料、来源信息和用户问题组合成 Prompt。
5. **生成答案**：LLM 根据检索结果生成回答，而不是只依赖模型内部知识。
6. **后处理**：进行引用标注、格式整理、安全检查，并记录反馈用于后续优化。

## 2. 为什么需要对文档进行 Chunk 切分？

Chunking 是将长文档拆成多个较小的文本块。RAG 需要进行 Chunk 切分，主要有以下原因：

1. **文档可能超过模型的长度限制**：Embedding 模型和 LLM 都有输入长度上限，过长的文档无法直接完整处理。
2. **用户问题通常只与局部内容相关**：如果直接检索整篇文档，会包含大量与问题无关的信息。
3. **整篇文档的语义容易被稀释**：一篇文档可能包含多个主题，使用一个向量表示整篇文档，很难准确表达其中每个局部主题。
4. **提高检索精度**：按 Chunk 检索可以直接召回与问题最相关的段落，减少无关内容对 LLM 的干扰。
5. **降低上下文成本**：只将命中的少量 Chunk 放入 Prompt，可以减少 Token 消耗。

## 3. 一个 Chunk 的结构通常是什么样的？

一个 Chunk 通常包含以下几个部分：

1. **Chunk ID**：文本块的唯一标识，用于查询、更新和去重。
2. **Content**：Chunk 的正文内容，是最终提供给 LLM 的主要信息。
3. **Metadata**：描述 Chunk 来源和属性的信息，例如文档 ID、标题、章节、页码、来源地址、创建时间和权限标签。
4. **Embedding**：Content 对应的向量表示，用于计算语义相似度和进行向量检索。
5. **关系信息（可选）**：例如上一个 Chunk、下一个 Chunk、父章节或父文档 ID，用于补充上下文和恢复文档结构。

一个简单的 Chunk 可以表示为：

```json
{
  "chunk_id": "doc_001_chunk_03",
  "content": "RAG 在生成答案前，会先从外部知识库中检索相关内容。",
  "metadata": {
    "document_id": "doc_001",
    "title": "RAG 基础介绍",
    "section": "工作流程",
    "page": 3,
    "source": "rag_intro.pdf"
  },
  "embedding": [0.12, -0.08, 0.35],
  "previous_chunk_id": "doc_001_chunk_02",
  "next_chunk_id": "doc_001_chunk_04"
}
```

实际存储时，正文、元数据和 Embedding 可能位于不同的存储系统中，但逻辑上共同组成一个可检索的 Chunk。

## 4. 常见的 Chunking 策略有哪些？

常见的文档切分策略包括：

1. **固定长度切分（Fixed-size Chunking）**：按照固定字符数或 Token 数切分，通常设置一定的 Overlap。实现简单、速度快，但可能从句子中间截断语义。
2. **句子或段落切分**：按照句号、换行和自然段切分，能够保留基本语义完整性，但 Chunk 大小可能不均匀。
3. **递归切分（Recursive Chunking）**：依次尝试按照章节、段落、句子和字符切分，直到 Chunk 满足长度要求，是通用文本中较常见的方案。
4. **文档结构切分（Structure-aware Chunking）**：根据 Markdown 标题、HTML 标签、PDF 章节、表格或代码中的类和函数进行切分，适合结构明确的文档。
5. **语义切分（Semantic Chunking）**：通过 Embedding 相似度或模型判断语义边界，在主题发生变化的位置切分。语义完整性较好，但计算成本更高。
6. **命题化切分（Propositional Chunking）**：使用 LLM 将文本转换成多个简洁、自包含的原子事实，每个命题作为独立检索单元。它适合事实密集型问答，检索粒度细，但会增加预处理成本和索引规模，还可能在改写时遗漏或改变原意。
7. **父子或层级切分（Parent–Child / Hierarchical Chunking）**：小 Chunk 用于精准检索，命中后返回对应的大 Chunk 或父章节，为 LLM 提供更完整的上下文。
8. **动态切分（Dynamic / Query-aware Chunking）**：根据用户问题或任务类型，在检索时动态决定需要组合或展开哪些内容，效果灵活但实现复杂。

### Contextual Retrieval（上下文化检索）

Anthropic 提出的 Contextual Retrieval 严格来说不是一种新的 Chunk 边界切分方法，而是对切分后的 Chunk 进行上下文化增强：**先根据完整文档为每个 Chunk 生成一段简短的背景说明，再将背景说明放在原始 Chunk 前面，然后建立向量索引和 BM25 索引。**

例如，原始 Chunk 是：

> 该公司的收入比上一季度增长了 3%。

加入的上下文可以是：

> 这段内容来自 ACME 公司 2023 年第二季度的财务报告。

上下文化后的 Chunk 同时包含“哪个公司、什么时间、什么文档”等信息，可以缓解切分后指代不明和背景丢失的问题，提高检索命中率。其代价是需要额外调用模型生成上下文，并增加索引文本长度，因此还需要校验生成的背景是否准确。

实际项目通常组合使用多种策略，例如：**先按照标题和段落递归切分，再设置少量 Overlap；为 Chunk 补充文档级上下文后建立混合索引；检索时使用小 Chunk 或命题召回，再返回对应的父章节或原始段落。**

简单来说：**命题化切分解决“检索单元不够细”的问题，Contextual Retrieval 解决“Chunk 切开后缺少背景”的问题；两者都可以和递归、结构化或父子切分组合使用。**

参考：[Dense X Retrieval](https://arxiv.org/abs/2312.06648)、[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)

## 5. 什么是 Embedding？如何选择合适的 Embedding 模型？

Embedding（向量表示）是将文本、图片等非结构化数据转换成固定维度的数值向量。语义相近的内容，其向量在向量空间中的距离通常也更近。

在 RAG 中，文档 Chunk 和用户 Query 会分别经过 Embedding 模型转换成向量，再通过余弦相似度、点积等方式找到最相关的 Chunk。

选择 Embedding 模型时，主要考虑以下因素：

1. **任务类型**：RAG 应重点关注模型的 Retrieval 能力，而不能只看文本分类或语义相似度成绩。
2. **语言和领域**：确认模型是否支持中文、多语言，以及金融、医疗、法律、代码等特定领域。通用排行榜成绩高，不代表在业务数据上一定最好。
3. **Query 与 Document 的使用方式**：部分模型需要为 Query 和 Document 添加不同的指令或前缀，必须按照模型要求使用，否则效果会明显下降。
4. **最大输入长度**：模型需要能够覆盖实际 Chunk 的长度。超过长度限制会被截断，造成信息丢失。
5. **向量维度**：维度越高通常需要更多存储空间、网络带宽和检索计算量，但维度高并不保证实际效果一定更好。
6. **效果指标**：可以先参考 MTEB 等公开榜单，再使用自己的 Query—Document 数据集测试 Recall@K、MRR、nDCG 等检索指标。
7. **成本和性能**：综合比较模型调用价格、推理延迟、吞吐量、并发能力和批量处理能力。
8. **部署与合规**：根据数据隐私、网络环境、许可证和运维能力，选择云端 API 或本地开源模型。

## 6. Embedding 算法演进

### 第一阶段：从词面表示到静态词向量

早期的 One-hot、TF-IDF 主要表示词的身份和出现情况；后来以 **Word2Vec** 为代表的方法，通过大量语料学习稠密词向量，使向量能够体现词之间的语义关系。但它的局限是**一个词通常只有一个固定向量，无法根据当前上下文区分不同含义**。([斯坦福自然语言处理小组](https://nlp.stanford.edu/IR-book/html/htmledition/dot-products-1.html))

### 第二阶段：从静态词向量到上下文表示

以 **2018 年的 BERT** 为代表，模型会结合上下文生成 token 的表示。例如，“吃苹果”和“苹果手机”中的“苹果”，能够得到不同的上下文表示。这一阶段解决了**同一个词在不同语境下如何表达**的问题，但模型具备语言理解能力，并不意味着直接取出的句子向量就适合做相似度检索。([arXiv](https://arxiv.org/abs/1810.04805))

### 第三阶段：专门为相似度和检索训练文本向量

**SBERT、SimCSE** 等工作进一步优化句子表示：SBERT 让句子能够独立编码，并通过余弦相似度比较；SimCSE 利用对比学习，让正样本对更接近、负样本更容易区分。随后，**E5 等模型**通过大规模文本对训练，将能力扩展到检索、聚类、分类等任务。([arXiv](https://arxiv.org/abs/1908.10084))

这里最关键的转变是：**不仅要生成向量，还要让向量之间的距离符合任务需求。** 配合 Bi-Encoder 架构，文档向量可以提前计算，查询时只需要编码问题并进行向量检索，从而兼顾语义匹配和检索效率。([Sbert](https://sbert.net/examples/cross_encoder/applications/README.html))

### 第四阶段：向通用化、多模态和高效率发展

近年值得关注的方向，我会重点讲四个：

**一是大模型化和指令化。** 使用大语言模型作为基础，再经过专门训练得到 Embedding，例如 **2025 年的 Qwen3 Embedding**；同时引入任务指令，让模型知道当前表示是用于检索、分类还是其他任务，而不是所有用途都采用相同的表示方式。([arXiv](https://arxiv.org/abs/2506.05176?utm_source=chatgpt.com))

**二是更细粒度、更多功能的检索表示。** 例如 ColBERT 的多向量、晚交互路线，保留 token 级信息进行细粒度匹配；**BGE-M3** 则进一步把稠密、稀疏和多向量检索整合到同一模型，同时支持多语言和长文本。([arXiv](https://arxiv.org/abs/2004.12832))

**三是多模态统一表示。** 不再只编码文字，而是将文本、图像、文档截图、视频映射到可比较的表示空间。例如 **2026 年的 Qwen3-VL-Embedding**，就支持这些模态之间的检索。([arXiv](https://arxiv.org/abs/2601.04720?utm_source=chatgpt.com))

**四是降低部署和检索成本。** 例如 Matryoshka，也就是“套娃”表示学习，让经过专门训练的向量可以截取前面较少的维度使用，在检索效果、存储空间和计算成本之间进行权衡。([arXiv](https://arxiv.org/abs/2205.13147))

因此，我理解这条发展主线是：**从“表示词的语义”，到“结合上下文理解文本”，再到“让向量适合具体任务”，最后扩展到更通用、更多模态和更高效的表示。**

另外，**Cross-Encoder 不应当被当作 Embedding 的下一代**。它是将查询和文档联合编码、直接评分的架构，通常与 Embedding 配合，形成“向量召回＋精细重排”的检索流程。([Sbert](https://sbert.net/examples/cross_encoder/applications/README.html))

flat：暴力搜索所有向量

kd-tree：把向量空间提前划分好，查询时剪掉“不可能包含最近邻”的区域。

lsh：Locality Sensitive Hashing，局部敏感哈希。相似向量-->较高概率得到相同 Hash-->进入同一个 Bucket

ivf：先粗定位，再局部搜索。首先对所有向量做聚类，例如 K-Means，每个 Cluster 有一个中心，找到最近的几个 Cluster，只搜索这些。

## 9. 向量数据库有哪些常见的性能调优方法？

向量数据库调优不能只追求低延迟，还要同时观察 **Recall@K、QPS、P95/P99 延迟、内存、磁盘和成本**。常见方法包括：

1. **选择合适的索引**：小数据或强精确性要求使用 FLAT；内存充足且要求低延迟、高 Recall 时使用 HNSW；内存有限时使用 IVF、PQ；数据无法全部放入内存时使用 DiskANN 等磁盘索引。
2. **调整 HNSW 参数**：增大 `M` 和 `efConstruction` 通常可以提高索引质量，但会增加建库时间和内存；增大查询时的 `efSearch` 可以提高 Recall，但会增加延迟。
3. **调整 IVF 参数**：`nlist` 控制聚类桶数量，`nprobe` 控制查询时搜索多少个桶。增大 `nprobe` 通常提高 Recall，但也会增加计算量。
4. **压缩向量**：使用 FP16、INT8、Scalar Quantization、Product Quantization 或 Binary Quantization，降低内存、磁盘和带宽消耗；必要时对召回结果使用原始向量重新排序。
5. **降低向量维度**：选择更低维的 Embedding，或使用支持 Matryoshka 的模型截取合适维度，可以减少存储和距离计算量，但需要重新验证检索效果。
6. **为 Metadata 建索引**：对租户、权限、时间、类别等高频过滤字段建立 Payload、倒排或 B-Tree 索引，避免先召回大量向量再进行低效过滤。
7. **控制 TopK 和候选集大小**：TopK、ANN 候选数和 Rerank 数量越大，Recall 可能越高，但延迟和成本也越高。通常先召回适量候选，再使用 Reranker 精排。
8. **合理设置分片和副本**：分片可以提高容量和写入吞吐量，副本可以提升查询并发和可用性；但分片过多会增加查询扇出、结果合并和运维开销。
9. **优化内存与磁盘布局**：将高频索引和热数据放入内存，将原始向量或冷数据放在 SSD；内存不足时可使用 mmap、量化或磁盘型索引。
10. **优化写入和索引构建**：批量写入代替逐条写入；大规模导入时合理安排索引构建、Compaction、Vacuum 和后台优化任务，避免与在线查询争抢资源。
11. **减少返回数据量**：如果业务不需要，不返回原始向量或大段 Metadata；降低网络传输、序列化和反序列化开销。
12. **持续压测和监控**：使用真实数据分布、过滤条件和并发流量测试，并将 ANN 结果与 FLAT 精确结果比较，避免只优化速度却导致 Recall 明显下降。

几种数据库的典型调优点：

| 数据库 | 常见调优方式 |
| --- | --- |
| **Milvus** | 根据数据是否放得进内存选择 HNSW、IVF、PQ 或 DiskANN；调整 `ef`、`nlist`、`nprobe`，并合理使用 mmap、分片和副本 |
| **Qdrant** | 调整 HNSW 参数，为高频 Payload 字段建立索引，使用 Scalar、Product 或 Binary Quantization，并根据冷热数据选择内存或磁盘存储 |
| **pgvector** | 选择 HNSW 或 IVFFlat；调整 `hnsw.ef_search`、`ivfflat.probes`，使用迭代扫描、`halfvec` 或二进制量化，并配置索引构建内存及 Vacuum |
| **Pinecone** | 控制 `top_k` 和返回字段，避免无用的 Vector 与 Metadata 返回；合理使用过滤、Namespace、并行查询和 Rerank，并持续关注查询成本 |

一个推荐的调优顺序是：

**建立基线 → 确定 Recall 目标 → 选择索引 → 调整查询参数 → 优化过滤 → 压缩向量 → 调整分片和副本 → 进行端到端压测。**

简单来说：**先保证召回质量，再通过索引参数、压缩、过滤和资源配置降低延迟与成本；每次调优都要重新测 Recall，不能只看 QPS。**

参考：[Milvus 索引选型](https://milvus.io/docs/index-explained.md)、[Qdrant 官方文档](https://qdrant.tech/documentation/overview/)、[pgvector](https://github.com/pgvector/pgvector)、[Pinecone 搜索优化](https://docs.pinecone.io/guides/search/search-overview)

## 10. 大模型使用 RAG 的在线工作流程是什么？

### 一、Query 预处理

常见的 Query 预处理方法包括：

1. **安全与权限检查**：识别敏感信息、恶意输入和 Prompt Injection，并确定用户能够访问哪些知识库、租户和文档。
2. **文本标准化**：处理错别字、大小写、全半角、繁简体、特殊符号、缩写、口语和单位等，使 Query 更适合检索。
3. **对话补全（Query Condensation）**：结合聊天历史，将“它怎么样”“上一个方案有什么问题”等依赖上下文的问题，改写成可以独立理解的 Query。
4. **意图识别与路由**：判断是否需要检索，以及应该查询产品文档、数据库、代码库、互联网还是其他知识源。
5. **实体和 Metadata 提取**：提取人物、产品、时间、地区、文档类型、部门和权限等条件，转换成结构化过滤条件。
6. **Query 改写或增强**：展开缩写、补充上下文、添加同义词或领域术语，使 Query 与文档表达方式更接近，同时保留原始意图。
7. **Multi-Query 扩展**：生成多个不同表达的 Query 并行检索，提高召回率，最后合并并去重结果。
8. **问题拆解（Query Decomposition）**：将需要多跳推理或包含多个子问题的复杂 Query 拆成若干子查询，分别检索后再汇总。
9. **Step-back Query**：将过于具体的问题改写成更高层、更通用的问题，用于补充背景知识。
10. **HyDE（Hypothetical Document Embeddings）**：让 LLM 先生成一个假设性答案或文档，再对它生成 Embedding 并进行检索。它只用于改善召回，不能把假设内容当成最终事实。
11. **生成检索表示**：为 Dense Retrieval 生成 Query Embedding，同时为 BM25 等 Sparse Retrieval 保留关键词、实体和精确术语。

### 二、召回与结果融合

1. **多路召回**：并行执行 Dense Vector Search、BM25、知识图谱、SQL 或其他数据源检索。
2. **权限与 Metadata 过滤**：确保只返回用户有权访问并符合时间、类型等条件的内容。
3. **结果融合**：使用 RRF、加权分数等方式合并多路召回结果，并进行去重。
4. **Rerank**：使用 Cross-Encoder 或 Reranker 对候选 Chunk 重新排序，选出最相关的少量内容。

### 三、上下文构造与生成

1. **上下文扩展**：根据命中的 Chunk 补充父 Chunk、相邻 Chunk、标题和来源，恢复必要的文档背景。
2. **上下文压缩**：删除重复和无关内容，在 Token 预算内保留支持回答的关键证据。
3. **Prompt 构造**：将系统指令、原始问题、检索证据和引用信息组合后交给 LLM。
4. **答案生成**：要求 LLM 基于证据回答，在证据不足时明确说明无法确认。
5. **后处理与校验**：检查引用、事实一致性、安全性和输出格式，并记录 Query、召回结果及用户反馈用于评测。

## 11. RAG 中常见的 Query Rewrite 方式有哪些？

Query Rewrite 的目标，是把用户原始问题转换成**更明确、更完整，并且更容易命中文档**的检索请求。广义的 Query Rewrite 不只是换一种说法，还包括补全上下文、扩展关键词、生成多条查询、拆分问题以及生成结构化过滤条件等。

### 1. 规则化与标准化（Normalization）

通过确定性规则修正 Query，例如：

- 纠正错别字，统一大小写、全半角和繁简体；
- 统一日期、数值和单位，如“去年”根据当前时间转换为“2025 年”；
- 展开缩写和别名，如“RAG”补充为“Retrieval-Augmented Generation”；
- 将产品旧名称、内部简称映射为知识库中的标准名称。

它适合术语明确、规则稳定的场景，速度快且可解释；缺点是覆盖范围有限，过度标准化还可能改变专有名词。

### 2. 对话补全（Standalone Query / Query Condensation）

结合聊天历史，把依赖上下文的问题改写成一条能够独立检索的 Query。

例如，对话正在讨论 ACME 公司，用户问“它去年赚了多少？”，可以改写为：

> ACME 公司 2025 年的净利润是多少？

它是对话式 RAG 中最常用的改写方式。需要特别防止代词指代错误、把“营收”误改成“利润”，或者对“去年”等相对时间计算错误。

### 3. 同义改写（Paraphrase Rewrite）

在不改变问题含义的前提下，将口语、含糊表达改成更接近知识库语言的表达。

例如：

> “怎么退钱？” → “用户申请退款的条件和操作流程是什么？”

它适合用户表达与文档表达差异较大的情况；缺点是 LLM 可能擅自补充条件，产生 **Query Drift（查询意图漂移）**。

### 4. Query Expansion（查询扩展）

在原始 Query 上补充同义词、别名、缩写、上下位词和领域术语，而不是只保留一条改写结果。

例如：

> “ACME 去年赚了多少”  
> 扩展为：“ACME 2025 净利润、归母净利润、net income、profit attributable to shareholders”

它能够缓解用户词汇与文档词汇不一致的问题，尤其适合 BM25 或混合检索；但扩展词过多会引入噪声，降低精确率。

### 5. Multi-Query（多查询改写）

让 LLM 从不同角度生成多条保持原始意图的 Query，分别召回，再通过去重、加权或 RRF 合并结果。

例如，原问题“RAG 如何提高准确率？”可以生成：

1. RAG 检索阶段有哪些优化方法？
2. 如何通过 Rerank 提高 RAG 的答案准确率？
3. Chunking、Embedding 和混合检索如何影响 RAG 效果？

它适合宽泛、表述方式多样或单次召回不稳定的问题，Recall 通常较高；缺点是检索次数、延迟和成本增加，而且低质量的改写会带来更多噪声。

### 6. Query Decomposition（问题拆解）

将复合问题或多跳问题拆成多个可以单独检索的原子子问题，再汇总检索结果。

例如：

> “比较 ACME 和 Beta 公司 2025 年的营收及净利润变化。”

可以拆成：

1. ACME 2025 年营收及同比变化是多少？
2. ACME 2025 年净利润及同比变化是多少？
3. Beta 2025 年营收及同比变化是多少？
4. Beta 2025 年净利润及同比变化是多少？

它适合比较类、多约束和多跳推理问题；缺点是子问题之间的依赖关系可能丢失，后续还需要对实体、时间和口径进行对齐。

### 7. Step-back Query（后退一步提问）

把过于具体的问题抽象成一个更高层的背景问题，同时保留原始问题进行检索。

例如：

> 原始问题：“为什么 HNSW 的 `efSearch` 增大后查询变慢？”  
> Step-back：“HNSW 查询阶段如何搜索候选节点，`efSearch` 控制什么？”

它适合需要背景知识或原理推理的问题；但抽象后的查询可能过宽，因此通常要把其结果与原始 Query 的精确检索结果结合，而不是直接替换原始 Query。

### 8. HyDE（Hypothetical Document Embeddings）

先让 LLM 根据问题生成一段“假设性答案或文档”，再对这段文本生成 Embedding，用它检索语义相似的真实文档。

例如，用户只问“向量库太慢怎么办？”，LLM 可以先生成一段包含“HNSW 参数、量化、Metadata 索引、TopK”等术语的假设性说明，再用该说明进行向量检索。

HyDE 适合原始 Query 很短、关键词不足或缺少标注数据的 Dense Retrieval 场景；缺点是假设文档可能出现幻觉并把检索带偏。**假设内容只能作为检索表示，不能作为回答事实。**

### 9. Query2Doc / 伪文档扩展

Query2Doc 同样让 LLM 生成与问题相关的伪文档，但常见做法是将伪文档或其中的关键词与原始 Query 拼接，用于扩展 BM25 或 Dense Retrieval 的查询表示。

它与 HyDE 的主要区别是：

- **HyDE** 更强调对假设文档做 Embedding，再执行向量检索；
- **Query2Doc** 更强调使用生成文档扩展原始 Query，可用于 Sparse、Dense 或混合检索。

它能补充潜在答案中的领域词汇，但同样存在幻觉、噪声和查询过长的问题。

### 10. 结构化改写（Query + Metadata Filter）

将自然语言问题改写为“语义查询 + 结构化过滤条件”，例如：

```json
{
  "query": "revenue growth and net profit",
  "company": "ACME",
  "year": 2025,
  "document_type": "annual_report"
}
```

它适合企业知识库中存在租户、权限、时间、部门和文档类型等字段的场景，可以显著减少无关候选；但如果错误地提取了过滤条件，可能直接造成零召回，因此应区分用户的硬约束和系统推测出的软约束。

### 11. 翻译与跨语言改写

将 Query 翻译为文档主要语言，或同时生成多个语言版本进行检索。例如，用户使用中文提问，而技术文档主要是英文，可以同时检索中文原问题、英文翻译以及未翻译的产品名和错误码。

它适合多语言知识库；风险是专有名词、实体和行业术语被错误翻译，所以这些内容通常需要原样保留或使用术语表约束。

### 12. 基于初次召回结果的反馈式改写（PRF）

先使用原始 Query 进行一次检索，再从排名靠前的文档中抽取高价值术语、实体或句子，扩展 Query 后进行第二次检索。这类方法也称为 **Pseudo Relevance Feedback（伪相关反馈）**。

它可以让 Query 更贴近当前语料库的真实词汇；但如果第一次召回结果就是错误的，第二次改写会进一步强化错误方向，因此需要设置相关性阈值或使用 Reranker 过滤。

## 12. 什么是多路召回？召回结果如何融合？

**多路召回**是指使用多种检索方式并行查找候选文档，利用不同检索方法的互补性提高 Recall。常见的召回路径包括：

- **关键词召回**：使用 BM25 或倒排索引，擅长匹配产品名、人名、错误码和专业术语；
- **向量召回**：使用 Embedding 和向量数据库，擅长匹配不同表达但语义相近的内容；
- **Metadata 或结构化召回**：根据时间、部门、文档类型等字段过滤，或者查询 SQL 数据库；
- **知识图谱召回**：根据实体及其关系查找关联知识；
- **多 Query 或多模型召回**：使用原始 Query、改写 Query 或不同 Embedding 模型分别检索。

例如用户搜索“支付失败 E102 怎么处理”，BM25 容易精确命中错误码 `E102`，向量检索则可能找到标题为“银行卡扣款异常解决方案”的语义相关文档。两路结合通常比单独使用其中一路更稳定。

不同召回路径返回的分数通常不能直接比较，因此需要进行结果融合。常见方法有：

1. **去重**：先根据文档 ID、Chunk ID 或内容相似度合并重复结果。
2. **加权分数融合**：先把各路分数归一化，再按照业务效果分配权重，例如：`0.4 × BM25 分数 + 0.6 × 向量分数`。优点是可调节；缺点是不同检索器的分数分布不稳定，权重需要持续评测。
3. **RRF（Reciprocal Rank Fusion）**：不直接比较原始分数，只根据文档在每一路中的排名计算融合分数：`score(d) = Σ 1 / (k + rank(d))`。一个文档如果在多路结果中都排名靠前，融合后的排名通常也会更高。它简单、稳定，是混合检索中很常用的方案。
4. **学习排序或 Rerank**：将融合后的候选集交给 Cross-Encoder、Reranker 或 LLM，根据 Query 与 Chunk 的相关性统一重新打分。这一步精度更高，但计算成本也更高。

典型流程是：

**BM25、向量检索等并行召回 TopK → 权限过滤 → 去重 → 加权融合或 RRF → 取候选 TopN → Reranker 精排 → 选择最终 Chunk。**

需要注意，**融合和 Rerank 不是一回事**：融合负责把多个召回列表合并成一个候选列表，Rerank 则使用更准确但更昂贵的模型重新判断候选内容与 Query 的相关性。

简单来说：**多路召回负责尽量“找全”，融合负责合并不同来源，Rerank 负责从候选结果中进一步“找准”。**

## 13. RAG 有哪些范式？一个成熟的现代 RAG 系统是什么样的？

RAG 范式描述的是：**检索、生成以及中间增强模块以什么方式组织和协作。**经典分类主要包括 Naive RAG、Advanced RAG 和 Modular RAG；GraphRAG、Corrective RAG、Self-RAG、Agentic RAG 等可以看作在模块化架构上的专项演进。

### 1. Naive RAG（朴素 RAG）

基本流程是：

**文档切分并建立向量索引 → 对用户 Query 生成 Embedding → 召回 TopK Chunk → 拼入 Prompt → LLM 生成答案。**

优点是架构简单、开发快、成本低，适合 PoC 和简单知识问答；缺点是容易出现 Chunk 缺少上下文、召回不准、TopK 内容重复以及模型无法判断证据质量等问题。

### 2. Advanced RAG（高级 RAG）

在 Naive RAG 的检索前、检索中和检索后增加优化模块：

- **检索前**：结构化解析、语义 Chunking、Contextual Retrieval、Query Rewrite、意图识别和问题拆解；
- **检索中**：Dense + BM25 混合检索、Metadata 过滤、多路召回和动态 TopK；
- **检索后**：RRF、去重、Rerank、父子 Chunk 扩展、上下文压缩和证据排序；
- **生成后**：引用检查、事实一致性检查和无答案判断。

优点是检索和回答质量更高、可控性更强；缺点是链路变长，参数、延迟、成本和调试难度都会增加。

### 3. Modular RAG（模块化 RAG）

不再固定使用一条流水线，而是把 Query Router、Rewrite、Retriever、Reranker、Memory、Generator、Verifier 等设计为可替换模块，根据问题动态组合。

例如：简单事实问题直接混合检索；比较类问题先拆解；全局总结问题路由到 GraphRAG；实时信息查询路由到搜索引擎；结构化数据问题路由到 SQL。

优点是灵活、易扩展，可以针对不同任务选择最合适的检索策略；缺点是编排、状态管理、评测和系统维护更加复杂。**目前成熟的生产级 RAG 通常以 Modular RAG 为总体架构。**

### 4. GraphRAG（图 RAG）

从文档中抽取实体和关系构建知识图谱，并对图中的社区和主题进行分层总结。查询时可以结合原始 Chunk、实体关系和社区摘要进行检索。

它适合关系查询、多跳推理，以及“这批文档的主要主题是什么”之类的全局问题；缺点是建图和更新成本高，实体与关系抽取错误还会传播到查询结果。它通常与向量 RAG 配合使用，而不是完全取代向量检索。

### 5. Corrective RAG 与 Self-RAG

- **Corrective RAG（CRAG）**：在检索后增加相关性评估；如果结果不可靠，就改写 Query、重新检索或使用其他知识源进行纠正。
- **Self-RAG**：让模型学习何时需要检索，并对检索内容和自身回答进行反思与评价。

这类范式解决“召回结果不可靠时是否还要继续生成”的问题，可以提高鲁棒性；缺点是需要额外模型调用、训练或判断步骤，而且模型的自我评价也可能出错。

### 6. Agentic RAG（智能体式 RAG）

由 Agent 根据任务进行规划，自主决定：

- 是否需要检索；
- 查询哪个数据源；
- 是否拆解或改写 Query；
- 是否需要多轮检索、调用工具或验证结果；
- 当前证据是否足够生成答案。

它适合跨数据源、多步骤研究和复杂任务；优点是适应性强，缺点是延迟与成本高、行为不够确定，还可能出现循环检索和错误工具调用。因此生产环境通常会限制最大步数、可调用工具、Token 预算和超时时间。

### 7. Multimodal RAG（多模态 RAG）

同时检索和理解文字、图片、表格、音频或视频。例如，回答财报问题时既检索正文，也检索表格和图表。

它适合文档理解、商品搜索和视频问答；难点是不同模态的解析、Embedding、结果融合和引用定位更加复杂。

### 一个成熟的现代 RAG 系统是什么样的？

不存在适合所有业务的唯一“最完善 RAG 产品”。更合理的说法是：一个成熟系统通常是**模块化、混合检索、自适应路由、可评测并且安全可运营的 RAG 系统**，由以下三部分组成。

#### 一、离线知识处理链路

1. **多数据源接入**：连接文档库、网页、数据库、代码库、知识图谱和业务 API。
2. **解析与清洗**：处理 PDF、OCR、表格和图片，去除模板噪声、重复内容及过期版本。
3. **权限与溯源**：保存租户、ACL、来源、作者、时间、版本和文档层级等 Metadata。
4. **结构化 Chunking**：按标题、段落、语义或命题切分，并保存父子 Chunk、相邻关系和上下文说明。
5. **多索引构建**：同时建立 BM25 倒排索引、Dense Vector Index；需要时增加图索引和结构化数据库索引。
6. **增量更新**：支持新增、修改和删除同步，避免知识库数据过期或出现重复版本。

#### 二、在线问答链路

典型流程是：

**鉴权与安全检查 → Query 理解与路由 → 按需改写或拆解 → 多源混合召回 → 过滤、去重与 RRF → Rerank → 上下文扩展与压缩 → LLM 生成 → 引用及事实校验。**

其中几个关键能力是：

1. **自适应检索**：简单问题走短链路；复杂问题才启用 Multi-Query、GraphRAG 或 Agentic 多轮检索。
2. **混合与多源召回**：结合 BM25、向量、SQL、图和实时 API，不把所有问题都交给单一向量库。
3. **上下文工程**：恢复标题和父 Chunk，删除重复内容，按证据价值排序，并控制 Token 预算。
4. **证据约束生成**：要求模型基于检索证据回答并提供引用；证据不足、冲突或过期时应明确拒答或请求澄清。
5. **迭代纠错**：当召回质量评估不合格时，允许有限次数的 Query 改写、换源和重新检索。

#### 三、评测、安全与运营闭环

1. **离线评测集**：维护真实问题及标准答案，分别评估检索和生成模块。
2. **检索指标**：Recall@K、MRR、nDCG、过滤正确率和 Rerank 效果。
3. **生成指标**：答案正确性、忠实度、引用准确性、完整性和拒答正确率。
4. **在线指标**：P95/P99 延迟、Token 与检索成本、错误率、缓存命中率和用户反馈。
5. **可观测性**：记录原始 Query、改写过程、路由决策、召回结果、Prompt、模型版本和引用链路。
6. **安全与权限**：在内容进入 LLM 上下文之前执行文档级或 Chunk 级权限过滤，并防御 Prompt Injection、敏感信息泄露和恶意文档污染。
7. **版本与回归测试**：修改 Chunking、Embedding、Prompt、模型或索引参数后，使用固定评测集进行回归测试和灰度发布。

## 14. 什么时候需要使用图数据库增强 RAG？

当问题的答案不仅取决于“哪个 Chunk 与 Query 最相似”，还取决于**实体之间的关系、路径和整体结构**时，可以考虑使用图数据库或 GraphRAG 增强普通 RAG。

### 适合使用图数据库的场景

1. **需要多跳关系推理**

   例如：“A 公司的实际控制人还投资了哪些与 B 公司存在供应关系的企业？”答案需要经过“公司 → 控制人 → 投资企业 → 供应关系”等多条边，单纯向量检索很难稳定完成。

2. **关系本身就是核心信息**

   例如⭐️⭐️⭐️**组织架构、股权关系、供应链、社交网络、设备拓扑、调用链和药物—疾病—基因关系、代码中函数调用**。此类问题不仅需要找到实体，还要知道实体之间是什么关系。

3. **需要全局总结和主题分析**

   例如：“这一批客户投诉主要围绕哪些问题，各问题之间有什么关联？”传统向量检索只返回与 Query 最相似的少量 Chunk，容易忽略分散在整个语料库中的全局主题。GraphRAG 可以利用实体社区和社区摘要回答此类问题。

4. **知识分散在多个文档中**

   一个文档介绍人物，一个文档介绍项目，另一个文档记录事件。如果它们通过统一实体关联，图可以把跨文档证据连接起来。

5. **需要实体消歧和统一标识**

   例如“苹果”可能指公司或水果，同一个客户也可能以中文名、英文名和内部 ID 出现。图中的实体标准化和关系约束有助于减少歧义。

6. **需要可解释的推理路径**

   在金融风控、合规、医疗和故障诊断中，除了答案，还需要展示“通过哪些实体和关系得到结论”。图查询路径比只返回相似 Chunk 更容易解释。

7. **业务本身已经拥有高质量知识图谱**

   如果企业已经维护商品、用户、权限、组织或设备关系图，那么让 RAG 查询现有图通常比重新把这些关系压缩成文本再做向量检索更合理。

### 图数据库使用方式

### 1. 离线：准备知识图谱

将文档分块，提取其中的**实体和关系**，合并重复实体后存入图数据库，并保留与原文片段的关联。同时，可以为文本块建立向量索引，方便后续语义检索。

例如，从文档中提取出：

> 订单服务 **依赖** 支付服务；支付服务 **依赖** 数据库 A。

### 2. 在线：检索并生成答案

**① 找到检索入口。** 用户提问后，通过实体匹配、关键词或向量检索，定位相关的实体或文本块。

**② 沿关系扩展检索。** 以这些结果为起点，根据问题沿图中的关系查询，找到相关节点、路径及原文证据，而不只是返回语义相似的文本。

例如，用户问“数据库 A 故障可能影响哪些服务”，就可以沿**反向依赖关系**，查到支付服务以及间接受影响的订单服务。

**③ 组织上下文，生成答案。** 将筛选后的关系信息和相关原文整理成文本，连同用户问题一起交给大模型生成回答，**不是把整个图数据库塞给模型**

## 15. RAG 中的幻觉是怎么产生的？如何解决？

RAG 能够通过外部知识降低 LLM 幻觉，但不能彻底消除幻觉。只要**正确证据没有被找到、错误证据进入上下文，或者模型生成了证据没有支持的内容**，都可能产生幻觉。

### 一、RAG 幻觉的主要来源

#### 1. 知识库和数据源的问题

- 知识库中根本没有答案，模型只能依赖参数知识进行猜测；
- 文档已经过期、相互冲突或本身包含错误信息；
- PDF、OCR、表格解析错误，导致数字、标题和正文错位；
- 重复文档、旧版本和低质量网页干扰检索；
- Chunk 切分破坏了语义，把条件、主体和结论分到了不同 Chunk。

这种情况下，即使 LLM 完全忠于上下文，答案仍可能在事实上是错误的。因此需要区分：

- **Faithfulness（忠实度）**：答案是否得到了检索证据支持；
- **Correctness（正确性）**：答案是否符合真实世界或标准答案。

模型可能忠实地复述了一份过期文档，Faithfulness 很高，但 Correctness 仍然很低。

#### 2. Query 理解和改写错误

- 对话补全时解析错了“它”“去年”等指代和时间；
- Query Rewrite 擅自添加、删除或改变了用户约束；
- 复杂问题没有拆解，导致只检索到了其中一个子问题；
- 实体消歧、翻译或 Metadata 提取错误。

这会导致系统检索的是一个“看似合理但并非用户真正提出的问题”，也称为 **Query Drift**。

#### 3. 召回和排序错误

- Embedding 语义相似不等于事实相关，召回了主题相近但不能回答问题的 Chunk；
- 只使用向量检索，遗漏了错误码、数字、人名等需要精确匹配的信息；
- TopK 太小导致漏召回，TopK 太大又引入大量噪声；
- Metadata 过滤错误，检索到了错误年份、地区、产品版本或无权限内容；
- Reranker 排序失败，把真正的证据排在后面；
- 多跳问题只找到了部分证据，模型自行补全了缺失链路。

#### 4. 上下文构造问题

- Chunk 缺少标题、父段落、表头或前置定义，脱离原文后产生歧义；
- 上下文过长，关键证据被截断或处于模型不容易关注的位置；
- 多个文档互相冲突，但 Prompt 没有要求模型识别冲突；
- 相同内容大量重复，使模型误以为重复次数代表事实可信度；
- 文档中的 Prompt Injection 被当作指令执行。

#### 5. LLM 生成阶段的问题

- Prompt 只要求“回答问题”，没有要求必须基于证据；
- 检索证据不足时，模型为了给出完整、流畅的答案而猜测；
- 模型的参数知识覆盖了检索到的新信息；
- 模型对证据进行了没有依据的因果推断、计算或信息拼接；
- 引用编号、来源、数字或专有名词在生成时被篡改；
- 即使降低 Temperature，也只能降低随机性，不能保证事实正确。

### 二、如何降低 RAG 幻觉？

解决幻觉不能只修改 Prompt，而应针对整个 RAG 链路分层治理。

#### 1. 提高知识库质量

- 对文档进行解析校验、去重、版本管理和过期数据清理；
- 保存来源、发布时间、版本、作者和可信度等 Metadata；
- 使用结构化、语义或命题化 Chunking，保留标题、父子关系和表头；
- 对关键数字、表格和业务规则尽量保存为结构化数据；
- 建立增量更新和删除同步机制，避免索引中的知识长期过期。

#### 2. 提高召回率和精确率

- 使用 BM25 + Dense Vector 的混合检索，兼顾精确术语和语义匹配；
- 根据问题使用 Query Rewrite、Multi-Query、问题拆解或 GraphRAG；
- 正确提取时间、版本、产品和权限等 Metadata 过滤条件；
- 使用 RRF 融合多路结果，再通过 Cross-Encoder 或 Reranker 精排；
- 根据 Query 难度动态调整 TopK，而不是所有问题使用固定值；
- 当首轮证据质量低时，采用 Corrective RAG：改写 Query、切换知识源或重新检索。

#### 3. 改善上下文构造

- 命中子 Chunk 后补充父 Chunk、标题、相邻段落和表头；
- 删除重复与低相关内容，并在 Token 预算内压缩上下文；
- 为每个证据分配稳定的文档 ID、Chunk ID 和来源链接；
- 优先放置最相关、最新和最可信的证据；
- 对冲突文档保留时间和版本信息，并明确要求模型说明冲突；
- 将外部文档视为“不可信数据”，隔离其中的指令，防止 Prompt Injection。

#### 4. 约束 LLM 基于证据生成

Prompt 中应明确要求：

- 只使用给定证据中的事实回答；
- 每个关键结论都要能够对应到引用；
- 不得编造不存在的引用、数字和来源；
- 证据不足时回答“根据现有资料无法确认”，而不是猜测；
- 证据冲突时列出不同说法，不擅自选择；
- 区分文档中的明确事实和模型自己的推断。

高风险场景还可以先抽取相关原文和结构化事实，再基于抽取结果生成答案；这通常比让模型直接阅读大量 Chunk 后自由生成更可控。

#### 5. 增加生成后的验证

1. **Claim 拆分**：把答案拆成若干可验证的事实陈述。
2. **证据对齐**：检查每条 Claim 是否能在引用 Chunk 中找到明确支持。
3. **引用校验**：确认引用真实存在，并且引用内容与结论对应。
4. **二次检索**：使用答案中的关键 Claim 再检索一次，寻找支持或反驳证据。
5. **规则与工具校验**：金额、日期和计算结果优先使用代码、SQL 或确定性规则验证。
6. **人工审核**：医疗、法律、金融等高风险决策不能只依赖自动验证。

需要注意，使用另一个 LLM 做 Judge 也不等于获得了事实保证，因为 Judge 自己也可能产生幻觉。更可靠的方式是把 LLM 判断与原文定位、结构化规则、标准答案和人工抽查结合起来。

#### 6. 建立分阶段评测与监控

- **检索阶段**：评测 Recall@K、MRR、nDCG，以及正确证据是否进入候选集；
- **生成阶段**：评测 Faithfulness、Answer Correctness、Citation Correctness 和拒答正确率；
- **端到端阶段**：评测完整性、延迟、成本和用户任务成功率；
- 保存 Query 改写、召回结果、Rerank 分数、Prompt、回答和引用链路，便于判断问题究竟发生在哪一层。

## 16. 有哪些 RAG 效果评估方法？

**检索效果（几个指标） → 生成效果（可以用llm评估） → 端到端效果（用户感受） → 鲁棒性与安全性 → 延迟和成本。**

从评估手段上，又可以分为**规则指标、LLM-as-a-Judge、人工评审和在线 A/B 测试**。

### 一、离线标准评测集（Golden Dataset）

首先准备一批具有代表性的测试样本，每条样本可以包含：

- 用户问题；
- 标准答案或答案要点；
- 必须召回的文档、Chunk 或事实；
- 正确引用；
- Metadata 过滤条件；
- 问题是否可回答，以及期望的拒答行为。

样本应覆盖简单事实、模糊表达、对话追问、多跳问题、无答案问题、冲突文档和权限场景。评测集既可以由领域专家标注，也可以由 LLM 合成后再进行人工抽查。

Golden Dataset 的优点是结果稳定、适合自动回归和方案对比；缺点是建设成本高，而且需要随知识库和业务变化持续更新。

### 二、检索模块评估

检索评估回答的问题是：**正确证据是否被找到了，并且排在足够靠前的位置？**

常见指标包括：

| 指标 | 含义 |
| --- | --- |
| **Hit Rate@K** | TopK 中是否至少出现一个相关文档 |
| **Recall@K** | 所有相关证据中，有多少被 TopK 召回 |
| **Precision@K** | TopK 结果中，有多少是真正相关的 |
| **MRR** | 第一个相关结果排名的倒数，越靠前分数越高 |
| **MAP** | 综合多个相关结果的 Precision 和排名 |
| **nDCG@K** | 在相关性有等级之分时，评价排序质量 |
| **Context Relevance** | 召回上下文与问题是否相关 |
| **Context Recall** | 回答问题所需的事实是否都进入了上下文 |

例如，正确 Chunk 排名第 1 和排名第 20，最终都可能被算作“召回成功”，但用户体验和生成效果完全不同，因此通常需要同时观察 Recall 和 MRR、nDCG 等排序指标。

还应分别比较 BM25、Dense Retrieval、混合检索、Query Rewrite、RRF 和 Rerank 前后的结果，定位提升究竟来自哪个模块。

### 三、生成模块评估

生成评估回答的问题是：**模型是否正确使用了检索证据？**常见维度包括：

1. **Answer Correctness（答案正确性）**：答案是否符合标准答案或真实事实。
2. **Faithfulness / Groundedness（忠实度）**：答案中的结论是否都能从检索上下文中得到支持。
3. **Answer Relevance（答案相关性）**：回答是否真正解决了用户问题，而不是包含大量无关内容。
4. **Completeness（完整性）**：标准答案中的关键要点是否都被覆盖。
5. **Citation Correctness（引用正确性）**：引用文档是否真实支持对应结论。
6. **Citation Completeness（引用完整性）**：需要证据支持的关键结论是否都有引用。
7. **Refusal Accuracy（拒答正确率）**：没有足够证据时是否正确拒答，有证据时是否避免错误拒答。

有标准答案时，可以使用 Exact Match、Token F1、ROUGE、语义相似度或按答案要点打分。开放式长答案不适合只使用字符串匹配，因为表达不同不代表答案错误，此时更适合使用 Claim 级证据校验、LLM Judge 或人工评分。

### 四、端到端与消融评估

端到端评估直接比较“用户问题 → 最终答案”的整体效果，例如任务成功率、答案正确率、引用正确率和拒答正确率。

但只做端到端评估无法定位问题，因此还需要进行 **Ablation Study（消融实验）**：

- 固定 Generator，只替换 Embedding、Chunking 或 Retriever；
- 固定检索结果，只替换 Prompt 或 LLM；
- 分别关闭 Query Rewrite、Rerank、GraphRAG 等模块；
- 对比不同 TopK、Chunk Size 和融合权重。

一种实用的错误归因方式是：

| 检索证据 | 最终答案 | 可能的问题 |
| --- | --- | --- |
| 正确 | 正确 | 系统正常 |
| 正确 | 错误 | Prompt、上下文构造或 Generator 问题 |
| 错误 | 错误 | 数据、Query、Retriever 或 Reranker 问题 |
| 不完整 | 部分正确 | TopK、多跳检索或上下文预算问题 |
| 无证据 | 仍然作答 | 拒答和幻觉控制问题 |

检索指标与最终答案质量并不总是完全一致，所以必须同时进行组件评估和端到端评估。

### 五、LLM-as-a-Judge 自动评估

将 Query、检索上下文、模型答案和可选的标准答案交给另一个 LLM，让它按照明确的 Rubric 评价相关性、正确性、忠实度、完整性和引用质量。

优点是能够评估开放式答案，速度快、易扩展，部分指标不需要标准答案；缺点是 Judge 也会产生偏差和幻觉，还可能偏爱与自身表达相似的答案。

使用时应注意：

- 将评价标准拆成单一、明确的问题，避免只让 Judge 给一个笼统总分；
- 要求输出评分依据和对应证据；
- 使用人工样本校准 Judge，检查其评分与专家是否相关；
- 重要评测可使用不同模型、多次投票或 Pairwise Comparison；
- Judge 模型、Prompt 和版本必须固定并记录，否则不同批次结果不可直接比较。

RAGAS、ARES 和 RAGChecker 都属于自动化 RAG 评测框架：RAGAS 强调无需人工标准答案的多个指标；ARES 使用合成数据、轻量 Judge 和少量人工标注进行校准；RAGChecker 更强调对检索与生成模块进行细粒度诊断。

### 六、人工评审

让普通用户或领域专家对答案进行盲评，评价正确性、完整性、可理解性、引用质量、安全性和业务可用性。

人工评审最接近真实需求，特别适合医疗、法律、金融和企业规则等高风险领域；缺点是速度慢、成本高，并且不同评审者可能标准不一致。因此需要明确评分 Rubric、准备示例，并统计评审者一致性。

实践中通常使用自动评测进行高频回归，再对关键样本、自动评分不确定样本和线上失败案例进行人工复核。

### 七、在线评估与 A/B 测试

将两个 RAG 版本分配给不同用户或流量，观察真实业务指标，例如：

- 点赞率、差评率和答案采纳率；
- 用户任务完成率、问题解决率和转人工率；
- 用户是否反复追问或重新搜索；
- 引用点击率和会话中断率；
- 业务转化率、客服处理时长等领域指标。

线上反馈最贴近真实价值，但容易受到用户群、问题难度和界面变化影响，不能简单把点赞率等同于答案正确率。A/B 测试还需要设置安全、延迟和成本等护栏指标。

### 八、鲁棒性与安全评估

除了正常问题，还需要构造压力和对抗测试：

- 问题无答案时是否拒答；
- 文档存在过期或冲突版本时能否识别；
- 加入无关 Chunk 后答案是否被干扰；
- 错别字、缩写、多语言和超长对话下效果是否稳定；
- 多跳问题是否找全证据；
- 恶意文档中的 Prompt Injection 是否会被执行；
- 用户能否检索到无权限 Chunk；
- 删除或更新知识后，旧内容是否仍被召回。

对应指标包括拒答准确率、冲突识别率、噪声敏感度、Prompt Injection 成功率和权限泄漏率等。

### 九、工程效果评估

一个回答很准但需要一分钟、成本过高或经常超时的 RAG，也不能算生产效果良好。因此还需要监控：

- P50、P95、P99 端到端延迟及各阶段耗时；
- QPS、并发能力、错误率和超时率；
- 每次请求的检索、Rerank 和 Token 成本；
- 索引构建时间、数据新鲜度和更新延迟；
- 缓存命中率、降级成功率和系统可用性。

## 17. RAG 的知识库动态更新是怎么设计的？

RAG 知识库动态更新的核心目标是：**让新增、修改、删除和权限变化尽快反映到检索结果中，同时避免重复数据、新旧版本混用、索引中断和脏数据。**

一个典型流程是：

**数据源变更 → 变更检测 → 消息队列 → 解析与 Chunking → Embedding → 写入暂存版本 → 校验 → 发布新版本 → 删除旧 Chunk → 清理缓存与监控。**

### 一、先区分需要处理的变更类型

| 变更类型 | 推荐处理方式 |
| --- | --- |
| 新增文档 | 解析、切分、生成 Embedding，并 Upsert 新 Chunk |
| 文档正文修改 | 生成新文档版本，重新解析、切分和 Embedding，成功后替换旧版本 |
| 只修改 Metadata | 直接更新 Metadata；正文没变时通常不需要重新生成 Embedding |
| ACL 或权限修改 | 立即更新过滤字段或撤回文档，优先级高于普通内容更新 |
| 文档删除 | 写入删除事件，删除或软删除该文档的全部 Chunk，并清理缓存 |
| Chunking 或解析规则升级 | 通常需要重建受影响文档，规模较大时建立新索引 |
| Embedding 模型或维度升级 | 新旧向量不能直接混用，应建立新索引并进行整体迁移 |
| 索引 Schema 或距离算法修改 | 构建新索引，验证后通过 Alias 或路由切换 |

### 二、如何检测数据发生了变化？

常见方式包括：

1. **事件驱动**：数据源通过 Webhook、对象存储事件、数据库 CDC 或消息队列发送新增、修改和删除事件，延迟低，适合实时性要求高的场景。
2. **定时增量扫描**：根据 `updated_at`、递增 ID、日志序号或 High-water Mark，只读取上次同步后的变化，适合不支持事件通知的数据源。
3. **内容校验和**：计算文件或标准化正文的 Hash；Hash 没变就跳过解析和 Embedding，避免无效重建。
4. **定期全量对账**：即使使用事件驱动，也应定期比较源数据与索引清单，补偿丢失事件、漏删文档和连接器异常。

通常采用“**事件驱动保证及时性 + 定期全量对账保证最终一致性**”的组合。

### 三、文档和 Chunk 如何做版本管理？

每个文档需要一个跨同步任务保持稳定的 `document_id`，并记录版本及处理配置，例如：

```json
{
  "document_id": "policy_123",
  "source_uri": "kb://refund-policy",
  "source_version": "v8",
  "content_hash": "sha256:...",
  "chunk_id": "policy_123:v8:chunk_03",
  "parser_version": "parser_v2",
  "chunker_version": "chunker_v3",
  "embedding_model": "embedding_v2",
  "updated_at": "2026-07-19T10:00:00+08:00",
  "effective_at": "2026-08-01T00:00:00+08:00",
  "status": "active",
  "acl": ["finance", "customer_service"]
}
```

`document_id` 用于定位同一份业务文档；`source_version` 和 `content_hash` 用于判断是否变化；`chunk_id` 应包含文档版本或内容 Hash，避免 Upsert 时误覆盖其他 Chunk；解析器、Chunker 和 Embedding 的版本则用于决定是否需要重新索引。

### 四、如何避免新旧版本同时被召回？

最危险的做法是先删除旧 Chunk，再慢慢生成新 Chunk：处理中途一旦失败，知识库会暂时没有该文档。更可靠的是“**先构建、后切换、再清理**”：

1. 将新文档版本标记为 `staging`；
2. 完成解析、Chunking、Embedding 和全部索引写入；
3. 校验 Chunk 数量、必需 Metadata、向量维度和抽样召回结果；
4. 原子地将新版本切换为 `active`，旧版本切换为 `retired`；
5. 查询时只检索 `status=active` 的版本；
6. 异步删除旧版本 Chunk，并保留短期回滚能力。

如果向量数据库无法对一个文档的多个 Chunk 进行事务更新，可以使用版本注册表、有效时间过滤，或者写入新的 Collection / Index 后通过 Alias 一次性切换。

### 五、增量更新与全量重建怎么选择？

#### 增量更新

适用于日常新增、正文修改、Metadata 变更和删除。只处理发生变化的文档，成本低、速度快。

#### 全量重建

以下情况通常需要重新建立整个索引：

- 更换 Embedding 模型、向量维度或距离算法；
- 大幅修改 Chunking、解析逻辑或 Contextual Retrieval 方式；
- 改变索引 Schema、分词器或核心 Metadata 结构；
- 旧索引出现大量重复、孤儿 Chunk 或难以修复的数据质量问题。

生产环境通常采用 Blue-Green 方式：

**继续使用 `index_v1` 提供查询 → 后台构建并测试 `index_v2` → 切换 `knowledge_current` Alias 到 `index_v2` → 观察指标 → 删除或保留 `index_v1` 用于回滚。**

这样可以避免重建期间服务中断，也能防止不同 Embedding 模型生成的向量混在同一索引中。

### 六、删除和权限更新如何处理？

删除必须作为一等公民来设计，否则容易出现源文档已经删除，但旧 Chunk 仍能被检索的“幽灵数据”。

- 删除事件应根据 `document_id` 清理对应的全部向量、倒排索引、图节点、缓存和派生摘要；
- 可以先将文档标记为 `deleted` 或写入 Tombstone，使查询立即不可见，再异步物理删除；
- 定期执行源数据与索引的删除对账；
- 如果只是权限被收回，应立即更新 ACL，并保证权限过滤在内容进入 LLM 上下文之前执行；
- 权限变更通常不能等待普通批处理，否则会形成短暂的数据泄漏窗口。

### 七、如何保证更新任务可靠？

1. **幂等性**：相同事件重复消费不能生成重复 Chunk；可以使用 `document_id + version + pipeline_version` 作为幂等键。
2. **顺序控制**：同一文档的更新按版本或事件序号处理，避免旧事件覆盖新版本。
3. **失败重试**：解析、Embedding 和写库分别设置有限重试和指数退避。
4. **死信队列**：持续失败的文档进入 DLQ，保留错误原因并等待人工或离线修复。
5. **断点续传**：批量同步记录 Checkpoint 和 High-water Mark，任务中断后从上次成功位置继续。
6. **限流与批处理**：批量生成 Embedding、批量 Upsert，避免更新任务影响在线检索延迟。
7. **可回滚发布**：新索引或新文档版本效果异常时，可以快速切回旧版本。

### 八、图和派生数据如何同步？

如果系统还使用 GraphRAG、父子摘要或问题索引，正文更新后不仅要更新向量：

- 重新抽取受影响的实体与关系；
- 删除旧文档独有的边，保留仍被其他文档支持的边；
- 更新相关社区和层级摘要；
- 重建受影响的父 Chunk 摘要、假设问题和关键词索引；
- 保存每条关系和摘要的来源文档，支持增量删除及溯源。

图的更新范围可能沿关系和社区向外传播，因此成本通常高于普通向量索引更新，可以使用批量异步更新，并在查询结果中记录图数据的新鲜度。

### 九、查询缓存和对话缓存如何失效？

知识更新后，旧的检索结果、语义缓存和生成答案缓存可能继续返回过期内容。常见做法是：

- 缓存 Key 中包含 `knowledge_version` 或索引版本；
- 为高时效数据设置较短 TTL；
- 根据受影响的 `document_id`、标签或 Namespace 主动删除缓存；
- 对政策、库存、价格等实时数据直接查询业务 API，不依赖长时间缓存的静态 RAG 索引。

### 十、需要监控哪些指标？

- 从源数据修改到可检索的 **Freshness Lag**；
- 待处理事件数、队列积压、处理吞吐和失败率；
- 解析、Chunking、Embedding、写索引各阶段耗时；
- 新增、更新、删除文档及 Chunk 数量是否匹配；
- 重复 Chunk、孤儿 Chunk 和新旧版本同时可见的数量；
- 数据源文档数与索引文档数的对账差异；
- 更新前后的 Recall@K、答案正确率、P95 查询延迟和成本。

## 18. RAG 系统落地的主要难点是什么？

### 1. 数据源质量和文档解析

企业数据往往分散在网页、PDF、扫描件、表格、代码库和业务数据库中，并且存在重复、过期、格式混乱和权限不一致等问题。

常见困难包括：

- PDF 阅读顺序错误，页眉页脚混入正文；
- OCR 识别错误，表格、图片和公式信息丢失；
- 同一制度存在多个版本，却无法判断哪个有效；
- 文档缺少标题、时间、作者和业务分类等 Metadata；
- 原始文档本身写得含糊，即使正确召回也无法回答问题。

因此，生产 RAG 的基础通常不是向量数据库，而是稳定的数据连接、解析、清洗、版本管理和质量治理流程。

### 2. Chunking 很难同时兼顾召回和上下文完整性

Chunk 太小容易丢失主体、条件和上下文；Chunk 太大则包含大量噪声，降低检索精度并消耗更多 Token。不同类型的文档也不能使用完全相同的切分方式。

通常需要结合标题结构、语义边界、父子 Chunk、相邻 Chunk、表格结构和 Contextual Retrieval，并使用真实问题验证 Chunk Size、Overlap 和召回效果，而不是只依靠固定字符数。

### 3. 用户 Query 复杂且不可预测

真实用户会使用错别字、缩写、口语、代词和模糊时间，也会提出比较类、多跳类或无法回答的问题。一个固定的“Query Embedding → TopK”流程无法覆盖所有问题。

系统需要处理对话补全、Query Rewrite、意图识别、Metadata 提取、问题拆解和检索路由，同时避免改写造成 Query Drift。简单问题应走短链路，复杂问题才启用 Multi-Query、GraphRAG 或 Agentic RAG。

### 4. 召回质量难以稳定

向量相似不等于事实相关。只使用 Dense Retrieval 容易漏掉错误码、人名和数字，只使用 BM25 又无法处理同义表达。

生产系统通常需要混合检索、多路召回、Metadata 过滤、RRF 和 Rerank，并针对不同 Query 调整 TopK。但候选集、融合权重和 Rerank 数量都会影响 Recall、延迟和成本，需要持续评测。

### 5. 多跳、关系型和全局问题难处理

答案可能分散在多个文档中，或需要先得到中间结论再继续检索。普通向量 RAG 擅长找局部相似内容，但不擅长稳定地完成跨文档关系推理和全局总结。

这类问题可能需要 Query Decomposition、迭代检索、SQL、知识图谱或 GraphRAG；但链路越复杂，错误传播、延迟和调试难度也越高。

### 6. 幻觉、引用和拒答控制

即使检索到了正确文档，LLM 仍可能遗漏条件、错误拼接数字、使用参数知识覆盖新信息，或者编造引用。检索结果错误或过期时，模型还可能忠实地生成一个事实错误的答案。

系统需要基于证据生成、Claim 级证据对齐、引用校验、冲突检测和答案后验证。更重要的是建立可靠的拒答机制：没有足够证据时应说明无法确认，而不是为了回答完整而猜测。

### 7. 缺少可靠的评测体系

RAG 参数很多，修改 Embedding、Chunking、TopK、Reranker 或 Prompt，都可能让部分问题变好、另一部分问题变差。如果没有固定评测集，只靠人工体验几个问题，很容易出现“感觉变好了”的假象。

需要建立包含问题、标准证据、答案要点和不可回答样本的 Golden Dataset，分别评估检索、生成和端到端效果，并结合 LLM Judge、领域专家和线上 A/B 测试形成回归机制。

### 8. 知识动态更新和一致性

生产知识库会持续新增、修改和删除内容。更新处理不当会出现旧文档仍能召回、新旧版本同时存在、源文件已删除但向量仍保留等问题。

系统需要支持 CDC、Webhook 或定时增量同步，建立稳定的文档 ID、版本和幂等机制，并采用“先写新版本、校验后切换、最后删除旧版本”的发布方式。Embedding 或 Chunking 整体升级时，还需要进行双索引迁移和灰度切换。

### 9. 权限、安全和合规

企业 RAG 不能只判断内容是否相关，还要判断当前用户是否有权访问。把无权限 Chunk 检索出来后再让 LLM 忽略是不安全的，权限过滤必须发生在内容进入模型上下文之前。

还需要防御：

- 恶意文档中的 Prompt Injection；
- 敏感信息和个人数据泄漏；
- 越权检索和跨租户数据串扰；
- 日志、缓存和评测数据中的二次泄漏；
- 模型或第三方服务对数据的保留与使用风险。

权限变化和删除请求必须快速同步，审计系统还要能够追踪答案使用了哪些数据。

### 10. 延迟、成本和系统扩展性

Query Rewrite、多路召回、Rerank、GraphRAG、Agent 多轮检索和答案验证都能提高效果，但也会叠加模型调用和网络延迟。

需要在质量与成本之间做权衡，例如：

- 根据问题难度动态选择模型和检索链路；
- 并行执行多路召回，批量生成 Embedding 和 Rerank；
- 控制 TopK、上下文长度和 Agent 最大步数；
- 使用查询缓存、Embedding 缓存和语义缓存；
- 设置超时、重试、熔断和降级策略；
- 同时监控 Recall、P95/P99 延迟、QPS 和单次请求成本。

### 11. 可观测性和问题定位

当答案错误时，需要判断究竟是文档不存在、解析错误、Query 改写错误、检索漏召回、Rerank 排错、上下文截断还是 LLM 生成错误。

因此需要记录完整链路：原始 Query、改写结果、过滤条件、各路召回结果、融合和 Rerank 分数、最终上下文、Prompt、模型版本、引用及耗时。如果只有最终答案日志，生产问题通常很难复现。

### 12. 业务边界和用户预期管理

RAG 并不适合所有问题。它擅长基于已有知识回答，但不能自动保证复杂计算、实时交易操作和高风险决策的正确性。

落地前需要明确：

- 哪些问题必须回答，哪些问题必须拒答或转人工；
- 数据的新鲜度和答案准确率目标；
- 用户需要搜索结果、摘要、建议，还是执行业务操作；
- 答案错误造成的风险和可接受成本；
- RAG 是否真正优于传统搜索、规则系统或 SQL 查询。

如果没有明确业务指标，即使技术指标很好，也难以证明系统产生了实际价值。
