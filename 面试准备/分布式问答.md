## 理论

### CAP理论

https://cloud.tencent.com/developer/article/1860632

一个分布式系统最多只能同时满足一致性（Consistency）、可用性（Availability）和分区容错性（Partition tolerance）这三项中的两项。

**一致性**

- 是指整个分布式系统的数据应该是一致的。

- 什么时候数据会变？增删改，统称写请求。
- 什么叫数据一起变化？
  - 写请求成功，那么不同节点都应该返回变化后的数据。
  - 有机器故障，那么**不应该返回数据**。

**可用性**

- 合理时间内给出响应结果（不能是报错、超时）

**分区容错性**

- 节点间因为网络故障或机器宕机，导致分区。
- 出现分区后，整个系统还应该正常运行。

**如何选择**

- CP：订单、支付、库存
- AP：搜索、推荐、浏览
- CA：没有这种组合。因为当集群发生网络分区之后，如果想要满足P，那么A、C只能选一个

### CAP到BASE

CAP最大的问题是一致性和可用性不应该是二选一。

CAP本身是没有考虑网络延迟的问题的，它认为一致性是立即生效的，但是，要保持一致性，是需要时间成本的，这就导致往往分布式系统多选择 AP 。

引申出BASE，即使无法做到**强一致性**，但应用可以采用适合的方式达到**最终一致性**。

BASE 理论是 ACID 在分布式场景中的替代品。

BASE 是一种**设计理念/指导思想**，并不是一定要满足几项。

### BASE

Basically Available(基本可用)，Soft State（软状态）和Eventually Consistent（最终一致性）

**基本可用**：允许损失部分的可用性（时间/功能）。

**软状态**：允许系统中的数据存在中间状态，并认为该状态不影响系统的整体可用性。

**最终一致性**：在期限过后，应当保证所有副本保持数据一致性状态。

## 分布式共识算法

让分布式系统中的多个节点之间对某个提案达到一致的看法

### 拜占庭将军问题

拜占庭将军问题描述的是分布式系统在存在**恶意节点**或异常节点时如何达成共识。它比普通宕机故障更难，因为拜占庭节点可以对不同节点发送不同消息，破坏正常节点之间的一致判断。Lamport 论文证明，在口信消息模型下，如果要容忍 `m` 个叛徒，需要至少 `3m + 1` 个节点；签名消息模型不再要求 `3m + 1`，因为矛盾命令可以被验证和传播。Paxos、Raft、ZAB 主要处理崩溃故障，默认节点不会恶意撒谎；PBFT 这类算法处理拜占庭故障，适合节点之间不完全互信的场景，并且通常需要 `3f + 1` 个副本容忍 `f` 个拜占庭故障。

### Basic Paxos

三种角色，三个阶段

1. Prepare：Proposer发出请求，Acceptor只接收提案编号更大的请求并回复，Proposer需要收获半数以上的Acceptor的支持
2. Accept：获得支持的Proposer拟定一个提案，同样也需要获得半数以上的Acceptor支持
3. Learn：决议形成，发送给所有的Learner

提案编号：分布式ID

Acceptor接受条件：提案编号越大越好

**问题**：1. 只能对**一个值**形成决议。2. 两个Proposer提案交替号交替变大，形成**活锁**。

### Multi Paxos

1. 需要共识的每个值对应一个Paxos实例，用InstanceID标识。
2. Proposer中选取一个Leader，唯一地提交Proposal，解决了活锁。

### Raft

正确性源于复制状态机地性质，只要日志的命令一致，顺序一致，状态机就是一致的。因此我们维护日志的一致性即可。

每个节点都属于三种状态之一：Leader,Candidate,Follower

**算法流程**

Raft中，Follower在选举超时后变为 Candidate并递增 term，向所有节点发送 （投票）RequestVote；获过半数选票后升级为 Leader。

Leader 通过定期心跳 (AppendEntries空消息) 维持任期，并把客户端指令作为日志条目附在后续AppendEntries中发送给 Followers。

当日志在多数节点落盘后，Leader将该索引标记为已提交并下发Apply，所有节点按序应用到状态机，从而保证一致性；若出现冲突，Follower 根据 Leader 的前置索引‑任期回滚并覆盖旧日志。 

**Raft缺点**

单个节点容易成为性能瓶颈，尤其是写请求需要经过 Leader。

Leader 故障后需要重新选举，期间会有短暂的服务不可用。

Raft 是偏 CP 的协议，发生网络分区时，少数派无法继续提交数据。

在跨机房场景下，Quorum 复制会受到网络延迟影响。

### ZAB协议

整个集群有2种模式，节点有3种角色4种状态，特别为 ZooKeeper 设计的

- **Leader（领导者）：** 集群中**唯一**的写请求处理者。它负责发起投票和协调事务，所有的写操作都必须经过 Leader。
- **Follower（跟随者）：** 可以直接处理客户端的读请求。收到写请求时，会将其转发给 Leader。在 Leader 选举过程中，Follower 拥有选举权和被选举权。
- **Observer（观察者）：** 功能与 Follower 类似，但**没有**选举权和被选举权。它的存在是为了在不影响集群共识性能（即不增加需要等待的投票数）的前提下，横向扩展集群的读性能。

对应的，集群中的节点通常处于以下四种状态之一：

- `LOOKING`：寻找 Leader 状态（正在进行选举）。
- `LEADING`：当前节点是 Leader，正在领导集群。
- `FOLLOWING`：当前节点是 Follower，服从 Leader 领导。
- `OBSERVING`：当前节点是 Observer。

消息广播模式（正常处理写请求）

崩溃恢复模式（Leader 宕机或网络异常）

### Gossip协议

>  Gossip 是信息传播协议，**不是共识算法**（如 Raft/Paxos）。共识算法保证强一致性与安全性，Gossip 只保证最终一致性，不适用于选主或状态机复制等需要强一致的场景。

优点：去中心化、简单、拓展性强

缺点：最终一致性、不允许恶意节点、消息冗余

过程：当一个节点有状态需要更新到网络中的其他节点时，它会**随机**（增加容错）的选择周围几个节点散播消息，收到消息的节点也会重复该过程，直至最终网络中所有的节点都收到了消息。这个过程可能需要一定的时间，由于不能保证某个时刻所有节点都收到消息，但是理论上最终所有节点都会收到消息，因此它是一个最终一致性协议。

设计了两种传播模式

- 反熵：每隔段时间就随机选择某个其他节点，然后通过互相交换自己的所有数据来消除两者之间的差异，实现数据的最终一致性。
- 传谣：一个节点一旦有了新数据之后，就会变为活跃节点，活跃节点会周期性地联系其他节点向其发送新数据，直到所有的节点都存储了该新数据。（适合节点动态变化的情况）

## API网关

Nginx（边缘） → SCG（内部网关） → 微服务

完成功能：请求转发 + 请求过滤

微服务背景下，一个系统被拆分为多个服务，但是像安全认证，流量控制，日志，监控等功能是每个服务都需要的，没有网关的话，我们就需要在每个服务中单独实现，这使得我们做了很多重复的事情并且没有一个全局的视图来统一管理这些功能。

### Spring Cloud Gateway

**请求过程：最主要的是断言和过滤**

**路由判断**：客户端的请求到达网关后，先经过 Gateway Handler Mapping 处理，这里面会做断言（Predicate）判断，看下符合哪个路由规则，这个路由映射后端的某个服务。

**请求过滤**：然后请求到达 Gateway Web Handler，这里面有很多过滤器，组成过滤器链（Filter Chain），这些过滤器可以对请求进行拦截和修改，比如添加请求头、参数校验等等，有点像净化污水。然后将请求转发到实际的后端服务。这些过滤器逻辑上可以称作 Pre-Filters，Pre 可以理解为“在...之前”。

**服务处理**：后端服务会对请求进行处理。

**响应过滤**：后端处理完结果后，返回给 Gateway 的过滤器再次做处理，逻辑上可以称作 Post-Filters，Post 可以理解为“在...之后”。

**响应返回**：响应经过过滤处理后，返回给客户端。

**断言**：URL中包含xxx，则映射到路由xxx

**如何实现动态路由**：Nacos注册中心，自动维护微服务路由

**过滤器有哪些**：

- **Pre 类型**：在请求被转发到微服务之前，对请求进行拦截和修改，例如参数校验、权限校验、流量监控、日志输出以及协议转换等操作。
- **Post 类型**：微服务处理完请求后，返回响应给网关，网关可以再次进行处理，例如修改响应内容或响应头、日志输出、流量监控等。

几个概念区分

1. 响应式编程

响应式编程是一种**以数据流和事件为中心的编程模型**。

核心思想是：

> 不主动阻塞等待结果，而是提前定义“数据到来之后要做什么”。

例如传统同步代码：

```
User user = getUser();
Order order = getOrder(user);
return order;
```

响应式代码：

```
getUser()
    .flatMap(user -> getOrder(user))
    .map(order -> ...);
```

它描述的是：

```
User 到来
   ↓
查询 Order
   ↓
Order 到来
   ↓
继续处理
```

2. Reactor

Reactor 是 Java 中常用的**响应式编程库**，Spring WebFlux 就基于 Reactor。

核心类型：

```
Mono<T>   // 未来产生 0 或 1 个数据
Flux<T>   // 未来产生 0 ~ N 个数据
```

例如：

```
Mono<User> userMono = getUser();

userMono
    .map(User::getName)
    .filter(name -> !name.isEmpty());
```

Reactor 通过 `map`、`flatMap`、`filter`、`subscribe` 等操作，把异步处理过程组织成一条数据流。

3. 回调

回调的思想是：

> 一个异步操作完成后，执行提前注册好的函数。

例如：

```
getUser(user -> {
    System.out.println(user);
});
```

表示：

```
发起 getUser
   ↓
先不等待
   ↓
User 返回
   ↓
执行回调函数
```

如果异步操作很多，普通回调容易出现层层嵌套：

```
getUser(user -> {
    getOrder(user, order -> {
        save(order, result -> {
            ...
        });
    });
});
```

也就是所谓的**回调地狱**。

### UUID

**优点**：生成速度通常比较快、简单易用

**缺点**：存储消耗空间大（32 个字符串，128 位）、 不安全（基于 MAC 地址生成 UUID 的算法会造成 MAC 地址泄露)、无序（非自增）、没有具体业务含义、需要解决重复 ID 问题（当机器时间不对的情况下，可能导致会产生重复 ID。

### Snowflake(雪花算法)

```
| 1bit 符号 | 41bit 时间戳(ms-自定义纪元) | 10bit 机器/机房ID | 12bit 毫秒内序列 |
```

#### 优点

- **去中心化**：无需中心号段服务，请求本机即可生成，延迟极低。
- **高吞吐**：纯内存运算，单机能轻松撑住高并发。
- **趋势递增**：按毫秒级时间排序，**B+Tree 主键写入更友好**（更少页分裂）。
- **短且可存为 BIGINT**：64 位整数，数据库/索引占用小，序列化高效。
- **可编码拓扑**：机房/机器位便于分片、回溯来源与排障。
- **实现简单**：少量状态（lastTimestamp、sequence、workerId）。

#### 缺点 / 隐患

- **强依赖时钟**：**时钟回拨**会导致重复或乱序；需做回拨保护（等待/熔断/逻辑时钟）。
- **跨语言坑**：JS Number 只有 53 位精度，需用 **BigInt/字符串** 传输存储。
- **容量上限受位数约束**：每毫秒**最多 4096** 个/节点；超出要阻塞或自旋。
- **寿命有限**：41 位毫秒 ≈ **69 年**（相对自定义纪元）；纪元选太早会“到期”。
- **运维要求**：**workerId 唯一分配**要可靠（避免冲突导致碰撞）。
- **信息可推断**：包含时间与拓扑，**不适合安全敏感/需脱敏**的场景（可混淆或二次编码）。
- **非绝对全局单调**：不同节点时钟不一致时会产生**跨节点乱序**（但总体仍“趋势递增”）。

#### 看门狗

解决问题：锁不能过早失效、崩溃进程要释放锁

原理：获取锁的时候添加<锁, 线程>到全局的ConcurrentMap后台，单线程定时扫描这个 Map，使用 Lua 脚本校验*仍由本线程持有*后执行续期，正常解锁会把条目从Map中删除。

#### Redis集群

问题：由于 Redis 集群数据同步到各个节点时是异步的，如果在 Redis 主节点获取到锁后，在没有同步到其他节点时，Redis 主节点宕机了，此时新的 Redis 主节点依然可以获取锁，所以多个应用服务就可以同时获取到锁。

解决：Redlock 算法的思想是让客户端向 Redis 集群中的多个独立的 Redis 实例依次请求申请加锁，如果客户端能够和半数以上的实例成功地完成加锁操作，那么我们就认为，客户端成功地获得分布式锁，否则加锁失败。

## 分布式事务

### 理论

> 把一件**跨多个系统/服务/库/MQ**的业务操作，做成对外看起来**要么全部成功、要么最终撤销到一致状态**的“单次操作“。

**柔性事务：**BASE理论+业务实践。柔性事务追求的目标是，我们根据自身业务特性，通过适当的方式来保证系统数据的**最终一致性**。比如TCC、Saga、MQ事务、本地消息表。

**刚性事务：**追求**强一致性**。比如2PC、3PC。

柔性事务和刚性事务的区别：

- **事务边界不同**：刚性事务把多个操作包成一个全局事务；柔性事务拆成多个已经独立提交的本地事务。

- **失败恢复不同**：刚性事务靠 `rollback`；柔性事务靠 **重试 + 补偿**。

- **工程复杂度来源不同**：刚性事务复杂在协调器、锁和协议；柔性事务复杂在 **状态机、幂等、补偿、异常恢复**。

### 2‑Phase Commit

| 阶段                    | 谁发起                 | 关键动作                                                     | 结果含义                                              |
| ----------------------- | ---------------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| **1 Prepare / Voting**  | 协调者 **Coordinator** | 向所有参与者发送 **prepare** 请求：“能否提交？”              | 参与者要么写「预提交日志」，锁定资源后回 **Yes / No** |
| **2 Commit / Rollback** | 协调者                 | - 若 **全部 Yes** → 发送 **commit**- 有 **任一 No / 超时** → 发送 **rollback** | 参与者根据指令执行真正的 **提交或回滚** 并释放锁      |

### XA 模式

XA 可以理解为 2PC 在数据库等资源层面的标准化落地。2PC 是提交协议，XA 是 X/Open 定义的 DTP 接口规范，规定了 TM 如何协调多个 RM 参与同一个全局事务。

典型流程是：

1. AP 发起全局事务，TM 负责生成全局事务上下文。
2. 各个 RM（例如不同数据库）执行本地事务，但先不真正提交。
3. TM 调用各个 RM 的 `prepare`，所有 RM 都准备成功后再调用 `commit`，否则调用 `rollback`。

XA 的优势是业务侵入低，数据库本身负责事务隔离和回滚能力，适合短事务、强一致、并发压力不太高的场景。缺点也很明显：事务期间数据库资源会被长时间占用，性能和可用性都容易受到影响。

### 3‑Phase Commit

2PC 的核心问题是：协调者故障时可能长时间阻塞参与者。

在 2PC 基础上插入一道 “**预提交**” 层，核心是 **消除阻塞 & 提前超时自决**。

3PC 并没有彻底解决分布式事务问题。

| 阶段             | 关键动作                                                     | 超时处理                                               |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------ |
| **1 CanCommit?** | 协调者询问参与者是否可以参与提交                             | 参与者超时没收到 → 直接 **Abort**                      |
| **2 Pre‑Commit** | 若全部 **Yes**，协调者发 **pre‑commit** 命令；参与者执行半提交并 **释放锁**，返回 ACK | 参与者超时没收到 → 自行 **Commit**（因大家都已半提交） |
| **3 DoCommit**   | 协调者收齐 ACK 后广播 **do‑commit**，参与者真正提交          | 协调者故障 → 参与者在阶段 2 已可自决                   |

### TCC（Try – Confirm – Cancel）

**一句话**：先把资源“锁一下”（Try），流程都 OK 再正式扣（Confirm）；流程有问题就反向解锁（Cancel）。

| 阶段              | 服务方要做的事                                               | 失败回滚策略                                                 |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Try**　预留     | ‑ 校验业务条件‑ 预留/冻结资源（库存、余额、房间…）‑ 记录幂等信息（事务 ID、状态） | 若 Try 自己失败 → 直接返回 Fail，不再进入后续阶段            |
| **Confirm**　确认 | ‑ 真正扣减资源 / 持久化数据‑ 删除冻结标记                    | Confirm **必须保证成功**（原则上不允许失败）；如果偶发异常，需**重试直到成功** |
| **Cancel**　补偿  | ‑ 释放 / 解冻资源‑ 将业务状态恢复到 Try 前                   | 仅在 Try 成功但后续流程失败或超时时调用                      |

### MQ事务

MQ 事务就是让 ‘发消息’ 也具备 **Commit / Rollback** 能力，用来保证消息状态与本地业务操作一致。

例如 RocketMQ 的事务型消息：Producer先发一条*Half Message*，再执行本地事务，成功就 `commit`，失败就 `rollback`；Broker 还有回查机制兜底。

这样就避免了 ‘数据库写成功但消息没发’ 或 ‘消息发出但随即回滚’ 的一致性问题。

### Saga

**Saga 事务**是一种 **“长事务（Long‑Running Transaction）”** 解决方案：

把一次跨服务的业务流程拆成 **N 个本地事务**，每个步骤成功后立即提交；一旦后续任何步骤失败，按 *相反顺序* 触发 **补偿（Compensation）** 操作来回滚已完成步骤，最终保持全局一致。

## 配置中心

微服务架构下，应用被拆分为大量独立部署的服务，每个服务都有自己的配置（服务地址、数据库参数、功能开关等）。配置项数量会随着服务数量、环境数量和集群数量一起增长。传统配置文件方式存在以下问题：

- **修改需重启**：无论配置在代码库还是外部文件中，很多应用都需要重启进程才能让新配置生效。
- **与发版耦合**：如果配置放在代码库中，配置变更往往要跟代码发版绑定，难以独立灰度和回滚。
- **安全性不足**：敏感配置（数据库密码、API Key）直接写在代码库中容易泄露。
- **缺乏权限控制**：无法对配置的查看、修改、发布等操作进行细粒度权限管控。
- **配置分散难管理**：多环境（开发/测试/生产）、多集群的配置分散在各处，难以统一维护。

此外，配置中心通常提供以下增强能力：

- **版本管理**：记录每次配置变更的修改人、修改时间、修改内容，支持一键回滚。
- **灰度发布**：先将配置推送给部分实例验证，降低变更风险（Apollo、Nacos 1.1.0+ 支持）。

**推送方式**

当配置发生变化时，配置中心会主动或“近似主动”地通知各个服务实例，让它们及时拿到最新配置

## RPC

### 什么是RPC

**RPC（Remote Procedure Call）** 即远程过程调用，通过名字我们就能看出 RPC 关注的是远程调用而非本地调用。

**为什么要设计RPC ？** 因为，两个不同的服务器上的服务提供的方法不在一个内存空间，所以，需要通过网络编程才能传递方法调用所需要的参数。并且，方法调用的结果也需要通过网络编程来接收。但是，如果我们自己手动网络编程来实现这个调用过程的话工作量是非常大的，因为，我们需要考虑底层传输方式（TCP 还是 UDP）、序列化方式等等方面。

![ChatGPT Image 2026年8月31日 22_50_07](/Users/bytedance/vscode/backend-knowledge/面试准备/assets/ChatGPT Image 2026年8月31日 22_50_07.png)

**客户端发起方法调用**
 业务代码调用客户端提供的 RPC 接口。对业务代码来说，这个调用形式通常和调用本地 Java 方法没有明显区别。

**客户端代理拦截调用**
 客户端的动态代理 / Stub 拦截这次方法调用，并收集本次调用所需的信息，例如：
 `服务名、接口名、方法名、参数类型、参数值、请求 ID` 等。

**构造并序列化 RPC 请求**
 RPC 框架把调用信息封装成一个 RPC Request，然后使用 Protobuf、Thrift、Hessian、JSON 等序列化协议，将对象转换成适合网络传输的字节数据。

**客户端发送请求**
 客户端网络模块通过 TCP、HTTP/2 等通信协议，将序列化后的请求发送给目标服务端。
 实际 RPC 框架中，这一步往往还会涉及**服务发现、负载均衡、连接池、超时控制**等逻辑。

**服务端接收请求**
 服务端网络模块监听端口并接收到客户端发送的字节数据，然后解析 RPC 协议的消息边界、请求头等信息。

**服务端反序列化请求**
 服务端根据双方约定的序列化协议，将字节数据还原成 RPC Request，得到：
 **调用哪个服务、哪个方法，以及具体参数是什么。**

**服务端定位并调用目标方法**
 RPC 框架根据服务名和方法名找到已经注册的服务实现，然后通过反射、生成代码或其他调用机制执行真正的业务方法。

**业务方法执行并得到结果**
 服务实现完成业务逻辑，得到返回值；如果执行失败，也可能得到异常信息。

**服务端构造并序列化响应**
 RPC 框架将返回值、异常状态、请求 ID 等信息封装成 RPC Response，再序列化为字节数据。

**服务端返回响应**
 服务端通过网络连接将 RPC Response 发送回客户端。

**客户端接收并反序列化响应**
 客户端网络模块收到响应后，根据请求 ID 找到对应的调用，并将字节数据反序列化成返回结果或异常。

**客户端代理将结果返回给业务代码**
 Stub / 动态代理把结果返回给最开始调用 RPC 方法的业务代码。

# 高性能

## CDN

Content Delivery Network：内容--静态资源，分发网络--就近访问

关注两个指标：

- **缓存命中率**：命中率越高，用户越少回源，源站压力越小。
- **回源耗时和回源错误率**：一旦回源链路变慢或源站错误增多，CDN 节点也会被拖慢。

CDN 缓存静态资源的方式主要有两种：**预热**和**回源**。

如何找到最合适的 CDN 节点？**GSLB（Global Server Load Balance，全局负载均衡）** 是 CDN 的大脑，负责多个 CDN 节点之间的协调调度，最常用的实现方式是**基于 DNS 的 GSLB**。也就是用户真正访问 CDN 节点之前，先通过 DNS 查询，让 CDN 的调度系统决定“你应该去哪个节点”。

## 负载均衡

**轮询（Round Robin）**：请求依次分发到各个服务器，简单均匀，适合服务器性能接近的场景。

**加权轮询（Weighted Round Robin）**：给性能更强的服务器分配更高权重，让它承担更多请求。

**随机（Random）**：随机选择一台服务器，请求量足够大时整体分布通常比较均匀。

**加权随机（Weighted Random）**：按照权重随机选择服务器，性能越强的节点被选中的概率越高。

**最少连接（Least Connections）**：优先选择当前连接数最少的服务器，适合请求处理时间差异较大的场景。

**加权最少连接**：同时考虑服务器权重和当前连接数，性能更好的机器可以承担更多连接。

**一致性哈希（Consistent Hash）**：根据用户 IP、请求 Key 等做哈希，将相同 Key 尽量路由到同一节点；节点增删时只影响部分请求，常用于缓存、分布式存储。

**IP Hash**：根据客户端 IP 计算目标服务器，使同一个客户端通常访问同一台机器，可以用于简单的会话保持。

**最短响应时间（Least Response Time）**：综合当前连接数、响应延迟等指标，选择预计响应最快的服务器。

**P2C（Power of Two Choices）**：随机挑两台服务器，再从中选择负载更低的一台，开销较小但负载均衡效果通常很好。

## 幂等性

多次相同请求对服务端资源产生的预期效果，和执行一次请求一致。

前端可以在用户提交请求后将按钮置灰，或者将按钮置为不可点击。这只能降低重复提交概率，不能作为幂等保证。用户可以刷新页面、重放请求、绕过前端，也可能由网关超时重试、消息队列重复投递触发重复调用。真正的幂等边界必须放在服务端，尤其是资金、库存、订单这类会改变业务状态的接口。

后端保证幂等性就稍微麻烦一点，方法也有很多种，比如悲观锁、唯一索引、去重表、乐观锁、分布式锁、Token 机制等。

## 限流算法

### 固定窗口计数

- **核心思路**：把时间切成固定大小的窗口（常见 1 秒 / 1 分），到达请求就把「当前窗口+主体」这个键的计数器 `INCR`，超过阈值直接拒绝。
- **优点**： 实现最简单：在 Redis 里 `INCR` 加个 `EXPIRE` 就能跑；适合对秒级、分钟级 QPS 做硬上限。
- **缺点**：窗口边界可能出现“**突刺**”——恰好卡在窗口交界处时，可瞬间放行 2 倍流量。
- **典型场景**：对外开放的 REST API 总量限额、短信平台「单手机号每分钟不超 N 条」等。

### 滑动窗口计数

>  改进固定窗口计数

- **核心思路**：把整个窗口再细分成 k 个子格（如 1 分钟拆成 6 个 10 秒格）。请求只更新当前子格计数，总 QPS = 当前窗口内所有子格之和。超过阈值则拒绝。
- **优点**：只维护 k 个数字，内存 O(k)；精度接近滑动日志，但成本更低。
- **缺点**：k 值越小，流量抖动越大；需要定时轮转子格并归零。
- **典型场景**：网关层面做 QPS 限流，既想避免突刺又要支撑高并发。

### 漏桶

- **核心思路**：请求先进入队列；系统以恒定速度把队首请求“漏”出去（可同步调用，也可写入 MQ）。
- **优点**：出口速率严格恒定，能起到「匀速」和平滑流量的作用；排队机制可吸收小范围突发。
- **缺点**：一旦排队溢出只能丢弃或报错；高峰时可能排很长队，平均延迟受限于漏速。
- **典型场景**：调用慢接口（短信供应商、第三方支付）、批量写库、日志上传等需要匀速下游的场合。

### 令牌桶

> 改进漏桶，能够一次处理突发流量（漏桶只是接住了流量，没有处理，所以不能说能够处理突发流量）

- **核心思路**：系统按固定速率往桶里投放令牌（r 个/秒，桶容量 b）。请求想通过必须先取走令牌；桶空就拒绝或排队。
- **优点**：对「平均速率」有严格限制，同时允许一次性突发最多 b 个请求；实现简单，可用 Guava `RateLimiter` 或 Envoy 内置令牌桶。
- **缺点**：若生产速率设置得太高，桶可能总是满，无法持续地为下游“背压”。
- **典型场景**：API 网关、CDN 回源、外部支付接口等既要控平均又要允许短暂突发的链路。

令牌桶算法：**懒补充**（按上次时间差补发），分布式场景可把“令牌发放+扣减”放在 **Redis Lua** 脚本里原子完成，或用 `RateLimiter`（Guava）等库。

```java
import java.util.concurrent.locks.ReentrantLock;

public class TokenBucket {
    private final long capacity;           // 桶容量（最大令牌数）
    private final double tokensPerSecond;  // 发放速率
    private double tokens;                 // 当前令牌数（可为小数以提高精度）
    private long lastNanos;                // 上次补充时间
    private final ReentrantLock lock = new ReentrantLock();

    public TokenBucket(long capacity, double tokensPerSecond) {
        if (capacity <= 0 || tokensPerSecond <= 0) throw new IllegalArgumentException();
        this.capacity = capacity;
        this.tokensPerSecond = tokensPerSecond;
        this.tokens = capacity;                  // 刚启动给满桶，允许初次突发
        this.lastNanos = System.nanoTime();
    }

    // 消耗 count 个令牌；成功返回 true，失败返回 false
    public boolean tryAcquire(long count) {
        if (count <= 0 || count > capacity) throw new IllegalArgumentException();
        lock.lock();
        try {
            refill();
            if (tokens >= count) {
                tokens -= count;
                return true;
            }
            return false;
        } finally {
            lock.unlock();
        }
    }

    private void refill() {
        long now = System.nanoTime();
        double deltaSeconds = (now - lastNanos) / 1_000_000_000.0;
        if (deltaSeconds > 0) {
            tokens = Math.min(capacity, tokens + deltaSeconds * tokensPerSecond);
            lastNanos = now;
        }
    }
}
```

使用

```java
TokenBucket bucket = new TokenBucket(100, 50.0); // 容量100，每秒补50
if (bucket.tryAcquire(1)) {
    // 允许通过
} else {
    // 被限流，走降级/排队
}
```
