### 高并发系统设计

要点就是：**先把目标（SLO/一致性）说清楚 → 用缓存和异步把读写压力分流 → 用约束兜底强一致 → 用限流/熔断/降级/隔离守住可用性 → 用可观测/容量/压测闭环验证。**
 面试时有数字、有策略、有落地、有兜底，你就很完整了。

#### 3~5 分钟框架

**目标假设（先把尺子立住）**

- 峰值 50k QPS（读多写少），日请求 10 亿；**SLO**：可用性 99.95%、P99 延迟 ≤ 200ms；
- 高可用：同城多 AZ，跨机房容灾（RPO ≤ 5min，RTO ≤ 15min）。

**总体架构**
 Client → **CDN**（静态/图片） → **API Gateway**（鉴权、限流、灰度） → **无状态服务集群**（K8s/HPA 滚动扩容）
 → **缓存层**（本地 Caffeine + Redis 集群） → **存储层**（MySQL 分库分表 + 读写分离 + ElasticSearch/OLAP）
 → **消息队列**（削峰、异步化、重试） → 下游（搜索、推荐、报表）

**核心策略**

1. **“三层缓存”**：CDN → 本地缓存 → Redis。热点保护、逻辑过期、互斥重建、随机 TTL 防雪崩。
2. **读写拆分 & 分库分表**：按用户/业务维度做 Sharding；全局 ID 雪花/Leaf；**唯一约束兜底强一致**（如一人一单）。
3. **异步化/削峰**：下单、积分、通知入 **MQ**；**幂等设计**（业务幂等键 + 去重表/幂等号）。
4. **流量治理**：**限流（令牌桶）**、**熔断（失败率/RT）**、**降级（兜底返回/关闭非必要功能）**、**隔离（线程池/连接池分仓）**、**负载均衡**。
5. **一致性模式**：单服务内事务 + **Transactional Outbox/CDC** 出站；跨服务 **Saga**；**至少一次 + 去重** 达到“**逻辑上的 Exactly-Once**”。
6. **弹性与发布**：自动扩缩容、预热、金丝雀/蓝绿发布、就地回滚。
7. **可观测**：指标（RED/USE）、日志、分布式链路追踪；**P50/P90/P99** 面板；**错误预算**驱动治理。
8. **容量估算**（快速给数）：
   - **利特尔法则**：并发数 ≈ QPS × 平均响应时间。若峰值 QPS=50k，P95=100ms → 并发 ≈ 5k。
   - 单实例承载并发=CPU 核 × (1+等待/服务时间)（IO 密集可高一些）。按每实例稳态 400 并发 → 需要 ~13 实例，预留 50% 余量，**投 20~24 实例** 跨 AZ 部署。

------

#### 可展开要点清单

1) 网关 & 流量治理

- **限流**：全局/每租户/每用户/每接口，令牌桶 + 预热（避免冷启动抖动）。超限**排队**或**快速失败**。
- **熔断 vs 降级**：
  - 熔断：下游失败率/RT 升高→短路一段时间（保护系统）。
  - 降级：在可控场景 **主动牺牲** 体验（关闭个性化、返回缓存/兜底值）。
- **隔离**：为不同下游/功能分 **线程池/连接池**（Bulkhead），一个崩不拖全场。
- **重试**：**幂等接口**才重试，**指数退避+抖动**，**携带截止时间**避免雪崩。

2) 缓存（读多写少的“杀手锏”）

- **命中流程**：本地 Caffeine（微秒级）→ Redis（毫秒级）→ DB。
- **热点保护**：
  - 互斥重建（分布式锁）+ **逻辑过期**（先返回旧值，异步刷新）；
  - 随机 TTL、防雪崩；**空值缓存** 防穿透；
  - **Key 拆分/多副本**（热点 Key 分片，比如计数分 64 槽聚合）。
- **一致性**：写路径**先落库**→删缓存（或异步双写、订阅 Binlog 同步）。

3) 存储与事务

- **读写分离**：写主读从；**读后写一致**用读写粘滞/版本号。
- **分库分表**：按访问最均衡的维度切（例如 userId）；跨分片聚合交给 ES/OLAP。
- **强约束兜底**：
  - 例如一人一单：**数据库唯一索引** `(user_id,voucher_id)` 是最硬的闸门；
  - Redis/Lua 只是**前置拦截**，最终一致靠 DB 约束。
- **跨服务一致性**：
  - **Transactional Outbox + CDC**：事务内写业务表与 Outbox；CDC 投递到 MQ，消费者处理并幂等。
  - **Saga**：长事务拆步，失败走补偿。

4) 异步化 & MQ

- 适合：削峰（下单写库）、耗时任务（消息/邮件/积分）、非关键链路。
- **幂等**：业务幂等键（订单号/幂等号）+ 去重表/唯一索引。
- **顺序 & 延迟**：按 Key 路由到同一分区/队列；DLQ 处理死信。
- **语义**：一般选择“**至少一次** + 幂等去重”。

5) 高可用与容灾

- **无状态服务**横向扩展；多 AZ 部署；**故障转移**（健康探测 + 连接超时短路）。
- **数据库**：主从 + 自动故障切换；**半同步**提高 RPO；定期备份/校验恢复演练。
- **发布**：灰度、蓝绿、金丝雀；特征开关；可回滚的 DB 变更（向前兼容）。

6) 性能工程与内核/运行时

- **连接复用**：HTTP/2、gRPC、连接池；Keep-Alive 超时合理。
- **线程池**：IO 密集型线程数 ≈ CPU 核 × (1 + 等待/计算)；设置**队列上限** + **拒绝策略**（快失败）。
- **JVM/内核**：
  - GC：G1/ZGC；关注 **P99 停顿**。
  - 文件描述符/端口范围、`somaxconn`、backlog、`tcp_tw_reuse` 等网络参数。
  - 对象/字节缓冲复用谨慎使用，避免“过度优化”带来复杂 Bug。

7) 可观测与容量管理

**现在好不好？**——用**指标 Metrics**看吞吐（QPS）、错误率、延迟（P50/P90/P99）、资源使用（CPU/内存/连接池/队列积压）。

**哪里慢？**——用**全链路追踪 Traces**把一次请求在网关→服务A→服务B→Redis/MySQL 的每段时间拆开，谁最慢一眼看出。

**为什么慢/错？**——用**日志 Logs**与 Trace 关联，查看那次请求的入参/关键分支/异常栈。

**影响多大？该不该报警？**——用 **SLO/SLI + Error Budget**（比如月内可容忍 0.05% 错误），按“**燃尽速率**”报警，避免被噪音吵醒。

**还可更细**：**持续性能剖析 Profiling/火焰图**看函数级 CPU/锁/分配热点，定位代码级瓶颈。

### CPU满如何排查

我会先用 `mpstat/vmstat/pidstat` 判断是 **usr/sys/iowait** 哪类问题，再用 `top -H` 锁定线程、`jstack`/`async-profiler` 火焰图定位方法。若是 **usr** 高，多半是算法/自旋；**sys** 高用 `strace/perf` 看系统调用和锁竞争；**iowait** 高检查磁盘/DB；并同步观察 **GC**（`jstat`）与 **容器 CPU throttle**（cgroup）。现场会限流/降级保核心，抓取证据后从代码、线程池、锁、GC、SQL 逐项优化。

------

0️⃣ 先确认：真“满”还是“看起来满”

```bash
uptime                              # 看 loadavg，是否明显 > CPU 核数
mpstat -P ALL 1 5                   # 各核使用率：%usr / %sys / %iowait / %soft
vmstat 1 5                          # r(就绪队列)、cs(上下文切换)、us/sy/wa
pidstat -u -r -w -t 1 5 <PID>       # 进程/线程 CPU、上下文切换、IO 等待
```

**判断分叉：**

- `%usr`高 → 代码/算法/自旋问题；
- `%sys`高 → 系统调用频繁（锁/网络/磁盘/内核开销）；
- `%iowait`高 → 被 IO 拖住，CPU“空耗”；
- `r` 持续 > CPU 核数、`cs` 很高 → 线程过多/竞争严重；
- 容器里看**并没有满**但响应慢 → 可能是 **cgroup CPU throttle**（见 5）。

1️⃣ 锁定“哪个进程/线程”在吃 CPU

```bash
top -b -n1 | head -30                       # 找到罪魁 PID
top -H -p <PID> -b -n1 | head -50           # 线程级别的 CPU
# 也可：
ps -eLo pid,ppid,tid,psr,pcpu,stat,comm --sort=-pcpu | head
```

把 **TID 转 16 进制**，用来在 jstack 里搜索：

```bash
printf "0x%x\n" <TID>
```

2️⃣ Java 侧快速剖析（方法级定位）

**A. 线程栈 & 死锁**

```bash
jstack <PID> > thread_dump.log               # 立即抓
# 或
jcmd <PID> Thread.print > thread_dump.log
# 在线分析：fastthread.io 上传即可
```

把上一步的 **nid=0xTID** 搜到对应线程，看它在跑什么。

**B. 30 秒火焰图（强烈推荐）**

- 有 `async-profiler`：

```bash
./profiler.sh -d 30 -e cpu -f /tmp/cpu.html <PID>
# 下载 /tmp/cpu.html 打开看“最高的那条火焰”
```

- 没有也可临时用 `perf`（需 root）：

```bash
perf record -g -p <PID> -- sleep 30
perf report
```

**C. GC 是否拖累 CPU**

```bash
jstat -gcutil <PID> 1s 20        # YGC/FGC 频率、各区使用率
jcmd <PID> GC.class_histogram    # 是否疯狂分配/泄漏
# 如果看到 YGC/FGC 高、应用停顿频繁，就是 GC 抖动/内存压力
```

3️⃣ 按“类型”继续深挖 & 快速处置

3.1 `%usr` 高（用户态，最常见）

表现：某几个 Java 线程长期 TOP1。
 怎么查：

- 火焰图/`perf top -p <PID>` → 看热点方法；
- `jstack` 对应 `nid` → 看是否**自旋**/**递归**/**大循环**/**正则/JSON 序列化**/**加密压缩**等 CPU 密集型。
   处置：
- **算法/数据结构优化**：O(n²)→O(n log n)；减少全量扫描；
- **批量/缓存/降精度**：如取“昨日TOP”替代实时；
- **关闭 Debug/频繁日志**（尤其是同步格式化）；
- JIT 相关：极端场景检查 CodeCache 满（`jcmd <PID> Compiler.codecache`）。

3.2 `%sys` 高（内核态）

表现：`perf top` 里多为 `futex*`、`send/recv`、`epoll_wait`、`copy_*_user`、软中断 `ksoftirqd`。
 怎么查：

```bash
strace -t -f -c -p <PID>           # 统计系统调用占比（短时跑几秒）
sar -n TCP,DEV 1 5                 # TCP 重传、队列、每网卡吞吐
ethtool -S <nic> | head            # 网卡软中断统计（必要时）
```

处置：

- **锁/竞争**：看到 `futex` 高、线程 `BLOCKED` 多 → 减小锁粒度、读写分离、减少全局队列；用 `Arthas thread -b` 看谁持锁。
- **网络 syscall 高**：批量/Nagle/缓冲区调优；客户端限流；减少小包；
- **软中断/ksoftirqd 高**：网卡中断亲和/多队列/升级内核。

3.3 `%iowait` 高（IO 等待）

怎么查：

```bash
iostat -x 1 5                      # 磁盘 util、await、svctm
pidstat -d -t 1 5 <PID>            # 进程/线程 IO
```

处置：

- **DB/磁盘热点**：加缓存/索引；合并写；落地异步化；
- **批处理**：拉宽批量、降采样；把冷路径迁离主实例。

3.4 **GC 频繁/分配风暴**

表现：`jstat` 看到 YGC/FGC 频密、`GC (Allocation Failure)` 不断。
 处置：

- **先救火**：临时调大堆/年轻代、降低并发度、开降级；
- **根因**：减少临时对象（Stream/装箱/拼接）、池化（byte[]/缓冲）；检查大对象直入老年代；必要时启用/调优 G1/ZGC。

3.5 **锁竞争/死锁**

怎么查：

```bash
jstack 看 "BLOCKED" 多、等待某一把 monitor
Arthas: thread -b          # 显示阻塞链
Arthas: thread -n 5        # 最耗 CPU 的前 5 个线程
```

处置：缩小临界区、拆分热锁、改无锁/队列、使用 `StampedLock/LongAdder` 等；修死锁顺序。

3.6 **线程过多/切换抖动**

信号：`vmstat` 的 `cs` 非常高、`r` 很大、`pidstat -w` 上下文切换多。
 处置：收敛线程池数量（CPU 密集型 ≈ 核数；IO 型可略放大）、合并业务线程、避免“每请求起线程”。

3.7 **容器 CPU 配额被限（隐藏的大坑）**

怎么查（cgroup v2 示例）：

```bash
cat /sys/fs/cgroup/cpu.max        # 如 "50000 100000" 表示 50% 一个核
cat /sys/fs/cgroup/cpu.stat       # throttled_* 很高=被节流
```

`kubectl top pod` 看不到，但**throttle**会让你“看似 CPU 不满、却很慢”。
 处置：调高 `limits/requests`，或避免过小的 `cpu.quota`；有些场景可关闭节流。

------

4️⃣ 现场固定证据（便于复盘）

- 采样 30s：`mpstat/vmstat/pidstat/top -H` 输出重定向到文件；
- `jstack` 连抓 3 份（间隔 5s）；
- 火焰图一个；`jstat -gcutil 1s 30`；
- 视情况 `perf record` 30s、`strace -c -p` 5s；
- 容器：把 `cpu.max` / `cpu.stat` 保存。

------

5️⃣ 常见“踩坑清单”与对策

- **自旋等待**（while(true) 轮询队列/标志位）→ 用 `BlockingQueue/park`；
- **过度重试**（失败即刻重试）→ 指数退避 + 熔断 + 幂等；
- **细粒度日志**（同步 format）→ 降采样、异步日志；
- **错误的限流位置**（内层限流无效）→ 入口限流＋队列削峰；
- **慢 SQL** → 打开 SQL 慢日志、EXPLAIN、索引命中监控；
- **JDK/依赖 Bug** → 升级 JDK、Netty、XML/JSON 解析库版本；
- **CodeCache 满/JIT 异常** → `jcmd <PID> Compiler.codecache`，必要时扩大或清理热点路径。

### 短链系统

把**很长的URL**映射成**很短、可分享的码**（短链接），并在用户点击时**快速重定向**到原始URL，同时**可控、可统计、可风控**的一整套服务。

它解决什么问题

- **可分享**：短信/社媒/线下二维码里更短更稳。
- **可管理**：可设置过期、禁用、A/B、Utm参数、品牌域名。
- **可统计**：点击量、访客去重、来源、地区、设备等。

基本工作流

1. **创建短链**
    客户端 → 短链API：提交长链接（可选：过期时间、是否自定义码、标签…）
    API 生成短码、入库，并把 `https://d.x/abc123` 返回。
2. **访问跳转**
    用户点击短链 → 跳转服务查码 → 校验（是否过期/封禁）→ 记录一次点击 → **302 重定向**到长链（常用 302，便于统计与灵活变更；永久不可变的才用 301）。
