# Agent 面试题

## 1. LLM、Workflow 和 Agent 的区别是什么？

- **LLM（大语言模型）**：负责理解、推理和生成内容，本质上是一个模型，可以看作 Agent 的“大脑”。
- **Workflow（工作流）**：按照人工预先设计好的固定步骤执行任务。每一步做什么、以什么顺序执行，通常都由程序提前定义。
- **Agent（智能体）**：围绕目标自主判断下一步做什么，并通过**规划、记忆、工具调用和结果反馈**不断调整行动。

## 2. Agent 分为几个模块？

1. **模型（Model）**：通常由 LLM 充当“大脑”，负责理解、推理和决策。
2. **规划（Planning）**：将复杂目标拆分成可以执行的步骤。
3. **记忆（Memory）**：保存上下文、历史信息和长期知识。
4. **工具与行动（Tools & Action）**：调用搜索、数据库、代码或外部 API 等工具执行任务。
5. **观察与反馈（Observation & Feedback）**：读取执行结果，判断是否达到目标，并调整后续行动。

## 3. 推理模式

### CoT（Chain of Thought，思维链）

普通llm回答问题：P(Next∣Question)

触发CoT之后：P(Next∣Question,Reasoning1,Reasoning2,Reasoning3)，这些reasoning不会加入到用户对话context

CoT 触发方式：

1. **Zero-shot CoT（零样本思维链）**：不给推理示例，只在提示词中要求模型分步骤思考，例如“请逐步分析这个问题”。
2. **Few-shot CoT（少样本思维链）**：提供几个包含中间推理步骤的示例，让模型模仿相同方式解决新问题。
3. **Structured CoT（结构化思维链）**：通过固定格式引导推理，例如要求模型依次输出“已知条件、分析、结论”。
4. **Auto-CoT（自动思维链）**：由程序自动选择问题、生成推理示例，再将这些示例用于后续任务。
5. **模型内化的 CoT**：通过监督微调、强化学习等训练，让模型在没有明确分步提示时也能进行多步推理。

### ToT（Tree of Thoughts，思维树）

相较于CoT，依赖外部 Agent 控制。

```
外部 Python / Agent Controller
        │
        ├── 调 LLM：生成 5 个思路
        │
        ├── 调 LLM：给 5 个思路打分
        │
        ├── controller 保留 top 2
        │
        ├── 再调用 LLM 展开
        │
        └── 最后选答案
```

### GoT（Graph of Thoughts，思维图）

将思路表示为图中的节点，将依赖关系表示为边。它不仅可以产生分支，还可以合并多个思路、复用已有结果，并通过反馈环继续改进。

## 4. Agent 常见的范式有哪些？

**ReAct（Reasoning + Acting）**：推理一步、执行一步、观察结果，再继续推理，如此循环。

Thought / Reasoning：模型先判断当前已知信息够不够、下一步要做什么。

Action：真正执行一个动作。

Observation： 获取 Action 执行后的结果，并把结果重新加入 Context。

**Plan-and-Execute（规划与执行）**：先把目标拆分成计划，再逐步执行；必要时根据结果重新规划。

**Reflection（反思与纠错）**：执行后由模型检查结果、总结问题并重新尝试，提高答案质量。

**Tool-Using Agent（工具调用）**：由 LLM 判断何时调用搜索、数据库、代码或 API 等工具，并根据返回结果继续处理。

**Multi-Agent（多智能体协作）**：多个 Agent 承担不同角色，通过分工、讨论或互相审核共同完成任务。

**Hierarchical Agent（分层智能体）**：由一个管理者 Agent 负责拆解和分配任务，多个子 Agent 负责具体执行。

ReAct 的主要缺点包括：

- **成本和延迟较高**：每轮都要经历“推理 → 行动 → 观察”，可能产生多次 LLM 和工具调用。
- **长程规划能力有限**：更关注当前一步，面对复杂的长期任务时可能缺少全局视角。
- **错误容易累积**：前一步推理或工具结果出错，可能导致后续步骤沿着错误方向继续执行。
- **可能陷入循环**：如果缺少最大步数、超时或完成条件，Agent 可能重复调用工具而无法停止。
- **结果稳定性不足**：LLM 输出具有随机性，相同任务的行动路径和最终结果可能不同。
- **存在安全风险**：Agent 可能受到错误工具结果或提示注入的影响，因此需要权限控制和结果校验。

常见的优化方式是加入全局规划、最大迭代次数、工具权限、结果校验、失败重试和 Reflection 机制。

这些范式可以组合使用。例如，一个多智能体系统中的每个 Agent 都可以采用 ReAct，并在执行后加入 Reflection。

## 5. Agent 的记忆模块中有哪几种记忆？

Agent 的记忆通常可以先分为两大类：

1. **短期记忆（Short-term / Working Memory）**：保存当前任务所需的上下文，例如对话历史、中间推理结果、工具返回值和当前计划。通常放在 LLM 的上下文窗口中，任务结束或超出窗口后可能丢失。
2. **长期记忆（Long-term Memory）**：将重要信息持久化保存，可以跨会话、跨任务使用，通常存储在数据库、向量数据库、知识图谱或文件中。

长期记忆还可以按内容分为：

- **情景记忆（Episodic Memory）**：记录过去发生过什么，例如某次任务的操作过程、结果和用户反馈。
- **语义记忆（Semantic Memory）**：记录事实和知识，例如用户偏好、业务规则、文档知识和概念之间的关系。
- **程序性记忆（Procedural Memory）**：记录如何完成任务，例如工作流程、工具使用方法、提示词模板和成功经验。

部分架构还会单独定义**感知记忆（Sensory Memory）**，用于暂时保存刚接收到的文本、图像、音频或环境状态，经过筛选后再进入短期或长期记忆。

一个典型的记忆处理流程是：

**收集信息 → 判断是否值得记忆 → 摘要或结构化 → 生成 Embedding → 持久化存储 → 根据当前任务检索 → 放回 LLM 上下文。**

## 6. Agent 中需要持久化的记忆一般如何存储？

不同类型的记忆通常会选择不同的存储方式：

1. **上下文窗口**：保存当前对话、计划和工具结果，适合作为短期工作记忆，但容量有限且通常不会跨会话保留。
2. **缓存或会话存储**：使用内存、Redis 等保存会话状态和临时结果，读取速度快，并可以设置过期时间。
3. **关系型或文档数据库**：使用 MySQL、PostgreSQL、MongoDB 等保存用户偏好、任务状态、事件记录等结构化或半结构化信息，支持精确查询和更新。
4. **向量数据库**：先将文本转换成 Embedding，再存入向量数据库；检索时根据语义相似度找回相关内容，常用于对话历史、文档知识和情景记忆。
5. **知识图谱**：以“实体—关系—实体”的形式保存知识，适合表达人物、事件和业务对象之间的复杂关系。
6. **文件或对象存储**：保存原始文档、图片、音频、代码和任务产物；数据库中通常只保存文件地址和元数据。

实际系统一般会组合多种存储：例如 Redis 保存当前会话，关系型数据库保存用户资料，向量数据库负责语义检索，对象存储保存原始文件。

为了避免记忆越来越多，还需要设置去重、重要性评分、过期时间、更新和遗忘机制；涉及个人或敏感信息时，还要进行权限控制和加密。

**什么时候取出来使用**：主动检索，任务开始前注入。被动触发，推理过程中，发起搜索。

拓展：向量数据库基本概念和基本操作。

## 7. Agent 的记忆压缩有哪些方法？

记忆压缩的目标是用更少的 Token 或存储空间保留完成任务所需的关键信息。常见方法包括：

1. **截断与滑动窗口**：只保留最近的内容，删除较早的信息。实现简单，但容易丢失早期的重要细节。
2. **选择性保留（Extractive Compression）**：根据相关性、重要性和时效性，只保留原文中的关键句、关键事件和工具结果。
3. **摘要式压缩（Abstractive Summarization）**：使用 LLM 将多轮对话或执行过程改写成更短的摘要，压缩率高，但可能产生遗漏或事实偏差。
4. **结构化压缩**：将自然语言历史转换成 JSON、表格或固定字段，只保留目标、约束、计划、进度、结论和未完成事项。
5. **分层摘要**：先生成局部摘要，再将多个局部摘要合并成更高层摘要，适合长期对话和大型任务。
6. **记忆合并与去重（Memory Consolidation）**：合并重复或相似的记忆，解决新旧信息冲突，并用最新、可信度更高的内容替换旧记录。
7. **基于检索的上下文压缩**：完整记忆保存在外部存储中，每次只检索与当前任务相关的少量内容放入上下文。它不一定减少存储总量，但可以显著减少输入给 LLM 的 Token。

压缩通常是有损的，因此需要优先保留：**系统指令、用户目标、关键约束、当前计划、重要事实、未完成事项和失败经验。**重要原始记录可以继续保存在外部存储中，便于需要时追溯。

实际系统通常采用组合方案：**近期内容保留原文，较早内容生成摘要，重复记忆进行合并，完整历史存入外部存储并按需检索。**

## 8. Single-Agent 和 Multi-Agent 一般怎么选择？

- **Single-Agent**：适合流程简单、步骤强关联、需要共享大量上下文，并且强调低成本、低延迟和稳定性的任务。
- **Multi-Agent**：适合任务可拆分、可并行，或者需要不同角色、工具、权限及交叉审核的复杂任务。

Multi-Agent 可以提升分工和并行效率，但也会增加模型调用成本、通信开销、状态一致性和调试难度。

简单来说：**默认优先使用 Single-Agent；当单 Agent 出现能力、上下文或执行效率瓶颈，且任务能够清晰拆分时，再使用 Multi-Agent。**

## 9. multi agent

按**协作决策权是否集中**，Multi-Agent 可以分为**中心化**和**去中心化**两大类，实际系统也可以组合成**混合方案**。这里关注的是谁决定任务分配和下一步行动，与 Agent 是否部署在多台机器上是两个维度。

### 中心化方案（Centralized）

中心化 Multi-Agent 是指系统中存在一个中心节点，负责管理其他 Agent，例如任务拆解、任务分配、状态维护、结果汇总和冲突处理；其他 Agent 主要负责执行具体子任务。

常见方案包括：

1. **Supervisor–Worker（主管—执行者）**：Supervisor 动态分配任务，Worker 返回结果，再由 Supervisor 决定下一步。
2. **Router–Expert（路由—专家）**：Router 判断任务类型，并将任务交给对应的专家 Agent。
3. **Planner–Executor（规划—执行）**：Planner 先生成计划，再由一个或多个 Executor 按计划执行，必要时重新规划。
4. **Workflow / Pipeline（工作流编排）**：中心编排器按照预设顺序调用不同 Agent，例如“研究 → 撰写 → 审核”。
5. **Blackboard + Controller（带中心控制器的黑板模式）**：各 Agent 读取共享工作区并写入结果，由中心控制器根据共享状态决定下一步。
6. **Judge / Aggregator（裁判或聚合器）**：多个 Agent 独立生成方案，由中心 Agent 负责评分、选择或合并结果。

简单区分：**Router 决定交给谁，Planner 决定分几步做，Supervisor 持续决定下一步，Workflow 按固定路线执行，Blackboard 管理共享状态，Judge 选择最终结果。**

中心化架构容易管理和调试，但中心节点也可能成为性能瓶颈和单点故障；如果中心 Agent 判断错误，还可能影响所有下游 Agent。

例如，LangChain 的 Subagents 模式由主 Agent 统一调用子 Agent，Router 模式由路由步骤选择专家，分别体现了中心协调和集中路由。[参考：LangChain Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)

### 去中心化方案（Decentralized）

去中心化 Multi-Agent 没有持续统一指挥所有 Agent 的中心决策者，各 Agent 根据自身状态、收到的消息和约定的协作规则，决定下一步行动。

常见的协作机制有以下几种，可以组合使用：

1. **Peer-to-Peer / Network（对等网络）**：Agent 直接向其他 Agent 请求协助、交换信息或协商分工。例如，研究 Agent 发现数据不足时，直接请求数据 Agent 补充，无需主管逐次批准。通信关系可以是全连接，也可以只连接相关角色。
2. **Handoff / Swarm（自主交接）**：当前 Agent 判断应由谁接手，并将任务、必要上下文和控制权交给对方。例如“客服 Agent → 退款 Agent → 支付 Agent”，每次交接由当前 Agent 决定。AutoGen 的 Swarm 就允许 Agent 作出局部交接决策。[参考：AutoGen Swarm](https://microsoft.github.io/autogen/0.7.3/user-guide/agentchat-user-guide/swarm.html)
3. **Peer Debate / Voting（对等讨论与投票）**：多个 Agent 提出方案、互相质疑和修订，再按约定的投票或一致性规则形成结果。如果改由固定的 Judge Agent 拥有最终裁决权，结果决策就带有中心化特征。
4. **Shared Blackboard / Event-driven（自主认领与事件协作）**：Agent 自主读取共享任务状态或订阅相关事件，认领任务、执行并发布结果，触发其他 Agent 继续处理。例如，研究结果发布后，写作 Agent 自主开始撰写。需要通过任务认领、版本控制或幂等机制避免重复执行和写入冲突。

去中心化方案适合角色自主性强、协作路径动态变化的任务，可以减少对单一决策者的依赖；代价是通信、状态一致性、冲突处理和调试更复杂，还可能出现反复交接、重复劳动或讨论不收敛，因此要约定交接条件、最大轮次、超时和结束条件。

**共享黑板或消息总线可以是公共基础设施，但不一定负责决策；反过来，多个 Agent 在群聊中交流，也不代表去中心化。判断关键是：谁决定下一步、谁分配任务、谁裁决结果。**去中心化决策也不代表底层存储或运行时没有单点故障。

### 混合方案（Hybrid）

结合中心化的全局协调与去中心化的局部自治。例如，总控 Agent 拆解目标、设定预算并验收结果，研究、编码和测试 Agent 在执行过程中直接协商、请求协助或交接任务。

混合方案适合既需要全局进度和质量控制，又需要团队内部灵活协作的复杂任务。**单纯的“主管 → 小组主管 → 执行者”仍属于分层中心化；只有部分协作决策交给 Agent 自主完成，才体现这里所说的混合方案。**

### Multi-Agent 是怎么传递消息的？

**本质上是由程序或 Agent 运行时，把一个 Agent 的任务请求、执行结果或状态变化，传给另一个 Agent 的消息处理逻辑；需要模型参与时，再将相关内容放入接收方的上下文并调用 LLM。**发送对象和消息内容可以由 LLM 通过工具调用决定，也可以由预设流程决定，实际投递由程序完成。

常见的传递方式有：

1. **进程内调用**：多个 Agent 在同一进程中运行，通过函数参数、返回值或内存队列传递消息。例如，主 Agent 把子 Agent 封装成工具，传入任务描述，执行后拿到结果。
2. **跨进程或跨服务调用**：通过 HTTP / RPC 等接口发送序列化消息，例如 JSON。请求中携带任务和上下文，接收方返回结果，或先返回任务 ID，后续再查询或回调通知。
3. **消息队列与发布订阅**：Agent 将消息发送到目标队列，或发布到某个主题，由接收方异步消费。适合任务解耦和多个 Agent 订阅同一事件；如果需要回复，可以发送一条带有关联 ID 的结果消息。
4. **共享状态或黑板**：Agent 将任务、进度和结果写入共享状态、数据库或文件，其他 Agent 通过读取、轮询或变更通知获得信息。这属于间接通信，需要处理并发写入和状态版本。

例如，AutoGen Core 支持指定接收方的直接消息，以及按主题发布、由订阅者接收的广播消息。[参考：AutoGen 消息与通信](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/framework/message-and-communication.html)

**消息传什么**：通常包含发送方、接收方或主题、任务 ID、消息 ID、消息类型，以及任务要求、必要上下文、结果或产物地址。消息正文可以是自然语言，也可以是结构化数据；大文件通常传地址，接收方按需读取。

例如，研究 Agent 完成检索后，发送“任务 ID + 结论摘要 + 来源链接”给写作 Agent；运行时将消息交给写作 Agent，后者把这些内容加入自己的上下文，再调用 LLM 生成文章。**各 Agent 不会天然共享完整上下文，需要显式选择传递哪些信息。**

中心化系统通常通过主管转发任务和汇总结果，去中心化系统通常由 Agent 直接指定接收方或发布事件；两者都可以使用上述通信方式。**Handoff 除了传递消息和必要上下文，还会把后续处理的控制权交给接收方。**

工程上还需要通过消息 ID 去重、任务 ID 关联请求与结果，并设置超时、重试和幂等处理，避免消息重复投递导致任务重复执行。
